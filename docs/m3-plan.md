## 1. プロジェクト概要（初見の人向け）

**MachiScape** は Mini Metro / Mini Motorways の系譜にあるミニマルなまちづくりWebゲーム。

- プレイヤーは**道路を引き**、**区画（住宅・商業・工業）を塗る**。建物は自動で建つ。
- 住民の車（人流）とトラック（物流）が実際に道路を走る。**渋滞は車の密度から自然に発生する**。
- 面白さの核は「渋滞せず人と物が流れる道路網を考えるパズル的な最適化」。
- ゲームオーバーは無い。エンドレスに街を育てる。
- **スマホ優先**のWebゲーム。PCも対応。無料公開予定。

### 技術構成

| 層 | 技術 | 場所 |
|---|---|---|
| シミュレーション | 純TypeScript（依存ゼロ・**決定論**） | `src/sim/` |
| 描画 | Pixi.js v8（WebGL） | `src/render/` |
| UI | React 19 + Zustand（**UI状態のみ**） | `src/ui/` |
| ゲームループ・入力 | 純TS | `src/game/` |
| ビルド/テスト | Vite / Vitest | — |

**絶対に守るルール**（`docs/implementation-spec.md` §0）:

1. `src/sim/` では `Math.random` / `Date` / DOM / Pixi / React を**使用禁止**（ESLintが機械的に弾く）。乱数は `src/sim/rng.ts` のシード付きRNGのみ。
2. **数値の直書き禁止。** バランス数値はすべて `src/sim/balance.ts` に集約する。
3. ユーザー向け文字列は `src/i18n/ja.ts` の `t()` 経由。コンポーネントに日本語を直書きしない。
4. 依存方向は `ui → render → sim`。逆流禁止（ESLintで強制）。
5. **同じ入力なら必ず同じ結果**（決定論）。走査順・タイブレークを固定する。テストで担保済み。

### 開発コマンド

```bash
pnpm install
pnpm dev        # 開発サーバ（--host 付き。スマホから http://<LAN or Tailscale IP>:5173/）
pnpm test       # Vitest
pnpm typecheck  # tsc --noEmit
pnpm lint       # eslint
pnpm build      # 本番ビルド
```

**注意**: TypeScript は 6.0.3 に固定してある。TS 7 は typescript-eslint が未対応で lint が起動しない。

## 2. 現在の状態（M2 完了時点）

### 動くもの

- チャンク（32×32タイル）単位のプロシージャルなマップ生成。川はチャンクを跨いで連続する
- 道路の建設・撤去。**8方向接続**（斜めを含む）。橋（水上）も可
- A* 経路探索。混雑度を辺コストに織り込むので、渋滞すると車が自発的に迂回する
- 区画を塗ると建物が自動で建ち、需要・満足度・退去・再入居が回る
- 人流（住宅→商業/工業）と物流（工業→商業）
- 日次の経済精算（税収・維持費）
- HUD（資金・人口・日数・速度・RCI需要バー）、ツールバー、トースト
- テスト162件緑。車両1500台で 2.02 ms/tick（予算5ms以内）

### 確定済みの設計判断（`docs/decisions.md` に詳細）

| ID | 決定 |
|---|---|
| D1 | 空間モデルは**グリッド**（自由曲線・ヘックスの試作と比較して決定） |
| D2 | 道路は**開始点から現在位置までの直線を常に表示し、指を離して確定**。行き過ぎても指を戻せば線も戻る |
| D3 | 道路グラフは**8方向接続**。斜めコスト√2・オクタイル距離ヒューリスティック |
| D4 | **M3 の主題を「街が読める」に変更**し、施設・マイルストーンを M4 へ後ろ倒しする（2026-07-30 承認） |

### 分かっている問題（この M3 で直すもの）

M2 の確認でオーナーから出た9点。すべて再現・原因特定済み。

加えて、計画改訂時のコード再読で**オーナーの指摘に無かった不整合を1件見つけた**（W1 で直す）:

- **建物のタイルに道路を引けてしまう。** `usableTiles` の `buildRoad` 検証は
  `isBuildableTerrain`（山だけを除外）しか見ていないため、建物の上に道路が敷ける。
  建物は `state.buildings` と `grid.buildingIndex` に残り続けるので、
  **道路の下で見えないまま税収と人口を出し続ける幽霊建物になる**。

## 3. M3 の目的と非目標

### 目的

**プレイヤーが街の状態を読み取れるようにする。** 具体的には:

- 何がうまく行っていて、何が詰まっているのかが**画面を見れば分かる**
- 数字が**何を意味し、何に繋がっているか**が分かる
- 車の動きが**街の営みとして読める**（片道で消えるのではなく、行って帰ってくる）
- 編集操作が窮屈でない（消せる・まとめて塗れる）

### 非目標（M3 ではやらない）

- ユニーク施設・マイルストーン・エリア拡張 → **M4**（元の M3 の内容）
- セーブ/ロード・効果音・タイトル画面・チュートリアル → M5
- バランスの本格調整・公開作業 → M6
- 鉄道・船・公共交通 → v2

### 完了条件

1. 下記 W1〜W4 の受け入れ基準をすべて満たす
2. `pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build` がすべて終了コード0
3. **オーナーのプレイテスト②**「街で何が起きているか分かるか」に合格

### W0: 継ぎ目を作る（**最初にこれだけを直列でやる**）

**担当ファイル**: `src/render/gameScene.ts`, `src/game/loop.ts`, `src/ui/store.ts`

#### なぜ要るか

W1〜W4 は一見独立だが、実際には次の3つを共有していて、放っておくと同じファイルを
別々のagentが書き換えて衝突する。

- インスペクタ（W3b）は**タップ入力**が要る → `loop.ts`。だが `attachPanZoom` のハンドラは
  現在 `onDragStart` / `onDragMove` / `onDragEnd` しか無く、タップとドラッグを区別していない
- オーバーレイ（W3a）は**描画レイヤ**が要る → `gameScene.ts`。だが `world` コンテナはクロージャの中で、
  `GameScene` が公開しているのは `markDirty` / `setPreview` / `render` / `destroy` / `app` だけ
- 矩形ドラッグ（W1）と選択状態（W3b）は**両方 `store.ts`** を触る

**この節は P0 で踏んだ失敗の再発防止でもある。** P0 では「比較したい軸以外を共通化せずに
3方式を並列発注し、3人が別々の地形生成を実装した」。**親が発注前に固定すべき契約の範囲を
見誤ると、並列化の利益が手戻りで消える。**

#### やること（**これ以外はやらない。機能は足さない**）

**0-1. `GameScene` にオーバーレイの口を開ける**

- `buildingLayer` と `previewLayer` の間に `overlayLayer: Graphics` を1枚追加する
  （**道路・建物より上、プレビューと車より下**）
  - **初版は「zoneLayer と roadShadowLayer の間」と書いていたが誤り。** 渋滞ヒートマップは
    道路タイルの混雑度を塗るものなので、道路より下に置くと道路の色に完全に隠れて何も見えない
  - プレビューと車を上に残すのは、建設中の操作と交通の流れがオーバーレイに埋もれないようにするため
- `GameScene` に `setOverlay(draw: OverlayDraw | null): void` を追加する。
  **描画の中身は W3a が書く**。型は次のとおり:

```ts
export type OverlayDraw = (g: Graphics, ctx: OverlayContext) => void;
export interface OverlayContext { state: GameState; congestion: CongestionMap }
```

- **`ctx` を `GameState` 単体にしないこと。** 渋滞ヒートマップの元データ `congestionEMA` は
  `GameState` ではなく `World.congestion`（`CongestionMap`）に載っている。
  `state` だけ渡すと W3a が渋滞オーバーレイを描けず、そこで契約の作り直しが発生する
- そのため **`GameScene.render` の第1引数を `GameState` から `World` に変える**
  （`loop.ts` は既に `world` を持っているので呼び出し側の変更は1行）。
  `render` 内で `world.state` を既存の描画に渡し、`overlayLayer` には
  `{ state: world.state, congestion: world.congestion }` を渡す
- `setOverlay` は `dirty = true` を立てる。`render` の dirty 分岐で `overlayLayer.clear()` してから
  現在の `draw` を呼ぶ
- **渋滞オーバーレイだけは dirty 任せにできない**（混雑度は毎tick変わるのに建設操作は起きない）。
  `draw` が「毎フレーム再描画を要るか」を申告できるようにするか、
  オーバーレイ有効時は毎フレーム `overlayLayer` だけ描き直す扱いにする。**後者で十分**
- W0 の時点では `draw` に `null` を入れておく（既定オフ＝何も描かない）

**0-2. タップを選択に繋ぐ**

**初版は「`attachPanZoom` に `onTap` を追加する」と書いていたが、`onTap` は既に実装済みだった**
（`src/render/camera.ts` の `PointerHandlers.onTap` / `TAP_SLOP_PX = 8`）。
実際に必要なのは `loop.ts` 側の配線だけだった。

現在の発火条件は `mode === 'pan' && !moved`、つまり**パンツール選択中に動かさず離したとき**。
建設ツール中のタップは従来どおり `onDragEnd`（＝1タイルの建設）になる。

- **この住み分けをそのまま採用する。** 初版は「タップと判定されたら `onDragEnd` を呼ばない」と
  書いていたが、それをやると**1タイルだけ道路を置く操作が失われる**。
  スマホで1マスだけ道を足すのは頻出操作なので、これを捨てる代償が大きい
- 代わりにインスペクタは**パンツール（「移動」）中のタップで開く**。パンは「眺める」モードなので、
  そこで詳細を見るのは操作として自然。押下時間の閾値（250ms）も不要になったので入れない
- `loop.ts` は `onTap` を受けて `worldToTile(w)` でタイルを求め、
  **`ui().setSelection({x, y})` を呼ぶだけ**にする（パネルの中身は W3b）
- **W3b への注意**: インスペクタは「移動ツール中のタップ」でしか開かない。
  初見のプレイヤーに伝わるかは W3b が UI で工夫すること（ツールバーのヒント等）。
  プレイテスト②で「詳細の出し方が分かったか」を確認する項目にする

**0-3. `store.ts` にスライスを定義する**

W1・W3 が使う状態を**先に全部定義しておく**（後から型を足すと衝突する）。

```ts
export type OverlayMode = 'off' | 'congestion' | 'satisfaction' | 'roadAccess' | 'zone';
export type DragShape = 'line' | 'rect';

// 追加するフィールド
overlay: OverlayMode;              // 既定 'off'
selection: TilePos | null;         // 既定 null（タップで入る）
setOverlay: (m: OverlayMode) => void;
setSelection: (p: TilePos | null) => void;
```

**0-4. ツールごとにドラッグの意味を切り替える口を作る**

`loop.ts` に `dragShapeFor(tool: Tool): DragShape` を置き、`road` は `'line'`、
`zone` と `demolish` は `'rect'` を返すようにする。
**`'rect'` の実装は W1 が行う。** W0 は関数と分岐だけ用意し、`'rect'` のときも
当面は既存の直線処理を呼んでよい（＝挙動を変えない）。

#### 受け入れ基準

- `pnpm typecheck` / `lint` / `test` / `build` が終了コード0
- **挙動が M2 から一切変わっていない**（オーバーレイは既定オフ、タップは選択だけで何も表示しない）
- タップ（短い接触）で道路が建設されないこと。ドラッグでは従来どおり建設できること
- W1〜W4 のブリーフに書かれた継ぎ目がすべて存在すること

### W1: 編集操作 — 消せる・まとめて塗れる

**担当ファイル**: `src/sim/world.ts`, `src/sim/types.ts`, `src/game/loop.ts`（W0 の後）, `src/ui/components/Toolbar.tsx`

**前提**: W0 の `dragShapeFor` と `store.ts` のスライスが入っていること。`store.ts` の型は追加しない。

#### 背景

- 区画を消す手段が存在しない（`eraseZone` は型だけあってUIから使われていない）
- 区画を塗るのが直線ドラッグなので、面を塗るのに何度もなぞる必要がある
- 道路を区画の上に引くと、**データとして区画が残ったまま重なる**（`buildRoad` が区画を消していない）

#### やること

**1-1. 道路を引いたら区画と建物を自動で消す**

`applyOp` の `buildRoad` で、道路を敷いたタイルの区画（`setZone(..., null)`）と、そのタイルにある建物を削除する。`grid.buildingIndex` からも削除すること。

- 理由: 道路と区画が同じタイルに同居する状態は、そもそも意味を持たない不整合。道路を優先する
- **費用は取らない**（区画の塗り直しは無料。道路建設費だけを取る）
- 建物を消したぶんの人口減は即座に反映される
- **これは見た目の問題ではなくデータの不整合（幽霊建物）の修正である。** 現状 `buildRoad` は
  建物タイルを弾かないので、道路の下に残った建物が `state.buildings` に居続け、
  `economy` の `computeTaxIncome` と `countPopulation` が数え続ける。
  プレイヤーには見えない人口と税収が発生する
- 建物を消したら、**その建物を目的地・出発地にしている車も消す**こと
  （`purpose.fromBuildingId` が一致する車、または `purpose.to` がそのタイルの車）。
  残すと存在しない建物へ向かい続け、`applyTripSuccess` が `find` で毎tick空振りする。
  既存の `removeVehiclesOnTiles` が `demolishRoad` で同じことをしているので、それに倣う
- **失敗トリップには数えない**（プレイヤーの操作による消滅。`demolishRoad` と同じ扱い）

**1-2. 矩形（範囲）選択**

ツールごとにドラッグの意味を変える。

| ツール | ドラッグの意味 |
|---|---|
| 道路 | **直線**（水平・垂直・45度にスナップ。D2で確定済み。変更しない） |
| 区画 | **矩形**（開始点と現在点を対角とする長方形を塗る） |
| 撤去 | **矩形** |

実装書 §12.3 は元から「区画: ドラッグで矩形塗り」と規定している。現状が仕様から逸脱しているので、仕様に合わせる修正。W0 が用意した `dragShapeFor()` の `'rect'` 分岐を実装する形にする。

- プレビューは確定後と同じ見た目で矩形を表示する
- 矩形が大きすぎるときの上限は設けない（費用で自然に制限される）
- **プレビューの検証コストに注意する。** `previewOf` は現在**1タイルにつき `opFor` + `canApplyOp` を
  1回ずつ**呼んでいる（[loop.ts](../src/game/loop.ts) の `previewOf`）。直線なら数十タイルで済むが、
  矩形だと 32×32 = 1024 タイルになり、これが `pointermove` ごとに走る。
  対策は次のどちらかでよい（実装者の判断）:
  - タイル単位の可否を専用の軽い述語に分ける（`canPaintTile(world, zone, t)` 等）。**推奨**
  - 直前の矩形と同じなら再計算しない（矩形の4隅が変わらない限りスキップ）
- 矩形の範囲計算は**開始点と終了点の順序が逆でも同じ矩形**になること（テストで担保する）

**1-3. 撤去ツールを拡張する**

現在の撤去は道路だけ。区画と建物も消せるようにする。

- 撤去ツールの矩形範囲内で、道路・区画・建物をすべて消す
- 費用は道路の撤去費のみ（区画・建物の撤去は無料）
- `BuildOp` に `demolishArea` を追加するか、既存の `demolishRoad` + `eraseZone` を組み合わせるかは実装者の判断でよい。**ただし1回の操作＝1回の `applyOp` にすること**（Undoの単位が壊れるため）

**1-4. PC: 左クリック長押しで削除**

PCで左ボタンを押したまま **400ms 動かさずにいると削除モードに入る**。そのままドラッグすると矩形範囲を撤去する。ボタンを離すと通常のツールに戻る。

- スマホでは実装しない（長押しはブラウザの選択・コンテキストメニューと競合しやすい）
- 削除モードに入ったことが分かるよう、プレビューの色を撤去色に変える

#### 受け入れ基準

- 区画の上に道路を引くと、区画表示が消える（重なりが視覚的に消える）
- 区画ツールでドラッグすると矩形が塗れる
- 撤去ツールで区画・建物が消せる
- PCで左クリック長押し→ドラッグで撤去できる
- **テスト**: 道路建設で区画・建物・buildingIndex がすべて消えること。矩形の範囲計算（開始点と終了点の順序が逆でも同じ矩形になること）

### W2: 描画 — 街の見た目を作り直す

**担当ファイル**: `src/render/gameScene.ts`（W0 の後・W2 が所有）, `src/render/theme.ts`

**前提**: W0 が `overlayLayer` と `setOverlay` を入れていること。**W2 はこの2つを消したり
層順を変えたりしないこと**（W3a がこの上に載る）。

#### 背景

- 交差点が太く潰れて見える（タイルごとに円を描き、その上に8方向の線を重ねているため）
- 車が三角形で、Mini Motorways のような愛嬌がない
- 建物が「入居/退去」の2値でしか描き分けられておらず、**発展の度合いが見えない**

#### やること

**2-1. 交差点をスリムにする**

現在の実装は、道路タイルごとに半径 `ROAD_W/2` の円を描き、さらに隣接方向へ太線を引いている。交差点では円＋8本の線が重なって塊になる。

- **道路幅を細くする**（`ROAD_W` 0.72 → 0.5 目安。最終値は見た目で決める）
- **円は「行き止まり・孤立タイル」にだけ描く**（隣接する道路が1つ以下のとき）。交差点では線が交差するだけになり、細く見える
- 道路幅は `balance.ts` ではなく描画の定数でよい（ゲームバランスではなく見た目のため）

**2-2. 車を Mini Motorways 風にする**

三角形をやめ、**角丸のカプセル（丸みのある長方形）**にする。

- 自家用車: 短いカプセル。進行方向に長い
- トラック: 長いカプセル。または「頭＋荷台」の2ブロック
- 色は `theme.ts` のトークンを使う。トラックは自家用車と色で区別する
- 影は小さく柔らかく（現状の方針を踏襲）

**2-3. 建物で発展の度合いを見せる**

現在は `occupied` の2値のみ。`satisfaction`（0〜100）が**描画に一切使われていない**。

- 建物のサイズを満足度で変える（満足度が高いほど大きく・濃く）
- 満足度が低い建物には**警告の印**を出す（小さなドット等。文字は使わない）
- 退去中の建物は薄いまま（現状踏襲）

この「見た目で分かる」ことが M3 の目的そのもの。凝る価値がある。

#### 受け入れ基準

- 交差点が塊に見えない（スクリーンショットでオーナーが判定）
- 車がカプセル型で、自家用車とトラックが見分けられる
- 満足度が低い建物が一目で分かる
- **性能**: 描画方式を変えても 60fps を維持（建物2,000・車両1,500想定）

### W3: 情報設計 — 数字の意味が分かるようにする

**このパッケージが M3 の本丸。** 曖昧さが最も大きいので W0 の直後に着手し、早めにオーナーに見せること。

**大きすぎるので3つに割る。別々にマージしてよい**（プリモーテムの死因②への対策）:

| 小分け | 内容 | 担当ファイル | 撤退可否 |
|---|---|---|---|
| **W3a** | 情報オーバーレイ（3-1） | `src/render/overlay.ts`（新規）, `src/ui/components/OverlayPicker.tsx`（新規）, `src/i18n/ja.ts` | 不可（M3の核） |
| **W3b** | インスペクタ（3-2）+ 需要バーの説明（3-3） | `src/ui/components/Inspector.tsx`（新規）, `src/ui/components/DemandBars.tsx`, `src/sim/growth/index.ts`, `src/sim/types.ts`, `src/i18n/ja.ts` | 不可（M3の核） |
| **W3c** | 街の状態サマリ（3-4） | `src/ui/components/CitySummary.tsx`（新規）, `src/i18n/ja.ts` | **撤退可**（§7） |

**W3a は `gameScene.ts` を触らない。** W0 が用意した `setOverlay(draw)` に描画関数を渡すだけにする。
**W3b は `loop.ts` を触らない。** W0 が用意した `store.selection` を読むだけにする。
この2つを守れば W2・W1 と並列に走れる。

#### 背景

オーナーの指摘: 「どのように発展しているかをもっとわかりやすくして」「パラメーターが分かりづらい、具体的になんの数字か、どこに連動しているか見たい」

現状の HUD は資金・人口・日数・RCI需要バーだけで、**その数字がどこから来てどこに繋がるかが分からない**。

#### やること

**3-1. 情報オーバーレイ（W3a / 実装書 §12.3 に規定済み・未実装）**

マップに重ねる表示モードを作る。**同時に有効なのは1つだけ。既定はオフ。**

| モード | 表示 |
|---|---|
| 渋滞 | タイルごとの混雑度をヒートマップで（`congestion` は既に sim が持っている） |
| 満足度 | 建物の満足度を色で（低い＝赤、高い＝緑） |
| 道路アクセス | 道路から遠すぎて建てられない区画タイルを警告色で |
| 区画 | 区画の色分けを強調（通常は薄く描いている） |

情報過多を避けるため、**切り替えは1タップで、オフに戻しやすいこと**。

4種すべて、**必要なデータは既に sim 側に揃っている**（新たな sim 変更は不要）:

| モード | データ源 |
|---|---|
| 渋滞 | `World.congestion`（W0 の `OverlayContext` 経由） |
| 満足度 | `state.buildings[].satisfaction` |
| 道路アクセス | `hasRoadAccess(grid, x, y, ROAD.ROAD_ACCESS_DISTANCE)`（`src/sim/grid.ts` が公開済み） |
| 区画 | `zoneAt(grid, x, y)` |

**3-2. インスペクタ（W3b / タップで詳細）**

マップ上の建物・道路タイルをタップすると、その要素の数字をパネルで表示する。
タップの検出と `store.selection` への格納は W0 が済ませているので、**W3b は `selection` を読んで描くだけ**。

建物の場合に見せるもの:

- 種別・入居/退去
- **満足度**（数値＋バー）と、**今それが上下している理由**（例: 「トリップ成功 +1/回」「在庫切れ −8/日」）
- 商業なら在庫、工業なら生産在庫
- 直近の到着/失敗の回数

**「どこに連動しているか」を必ず添える**こと。数字だけ出しても分からないというのが元の指摘。

**ここだけ sim 側の変更が要る（重要）。** 「今それが上下している理由」は現状**どこにも記録が無い**。
満足度の増減は3か所に分散していて、結果の数値だけが残る:

| 場所 | 増減 |
|---|---|
| `src/sim/traffic/trips.ts` の `applyTripSuccess` / `applyTripFailure` | +1 / −4 |
| `src/sim/traffic/index.ts` の `timeout` | −4 |
| `src/sim/growth/index.ts` の `updateSatisfaction` | 50への回帰 ±1、在庫切れ −8 |

対応は**最小限にする**。`Building` に日次カウンタを2つ足し、理由の文章は UI 側で組み立てる:

```ts
// src/sim/types.ts の Building に追加
tripsOkToday: number;    // 今日の到着数
tripsFailToday: number;  // 今日の失敗数（noPath / timeout の合計）
```

- 加算は上の3か所（`applyTripSuccess` / `applyTripFailure` / `timeout`）で行う
- **`updateSatisfaction` の末尾で 0 にリセットする**（日次の集計なので）。
  リセット位置は `world.ts` の `stepDay` が `progress.tripsToday` を空にしているのと同じ考え方
- **満足度の増減の内訳そのものを配列で持たせないこと。** 建物2,000棟ぶんの履歴配列は
  セーブ（§13）とメモリを無駄に膨らませる。在庫切れ・回帰・退去猶予は
  `stock` / `satisfaction` / `lowSatisfactionDays` から UI 側で言い当てられる
- `construct` / `reoccupy`（`src/sim/growth/index.ts`）で 0 初期化すること。
  **決定論テストは state のハッシュを取っているので、フィールド追加で既存テストの期待値が動く場合がある。**
  落ちたら期待値を更新してよい（挙動が変わったわけではないことをテスト内コメントに残す）

**3-3. 需要バーの説明（W3b）**

RCI需要バーをタップすると、その需要が**何で決まっているか**を式ではなく言葉で見せる。

例（住宅需要の場合）:
- 「働き口が足りている: +」「住民が多すぎる: −」「目的地に着けない車が多い: −−」

現在の内訳値（jobs / workers / 失敗率）も併せて出す。

**内訳は sim 側から出すこと。** `computeDemand`（`src/sim/growth/index.ts`）は `jobs` と `workers` を
関数内のローカル変数で計算して捨てており、返しているのは RCI の3値だけ。
`currentStats` から取れるのは `recentTripFailRate` までで、jobs / workers は取れない。

- **UI 側で数式を再実装しないこと。** 係数（`DEMAND.R_JOB_BALANCE_WEIGHT` 等）を UI に写すと
  balance.ts の一元管理が崩れ、後のバランス調整で表示と実挙動がずれる
- 対応: `Demand` に内訳を足すか、`explainDemand(state, stats)` を `growth/index.ts` に新設して
  `{ jobs, workers, failRate, contributions: {...} }` を返す。**後者を推奨**
  （`Demand` は `pipeline.ts` の契約で `processMoveIn` も受け取るため、表示専用の値を混ぜたくない）

**3-4. 街の状態サマリ（W3c・撤退可）**

「どのように発展しているか」への直接の答え。以下を1画面で見せる:

- 人口の推移（直近30日。`progress.dayReports` に日次レポートが既に溜まっている）
- 収支の推移
- いま街のボトルネックは何か（例: 「商業が足りない」「トリップ失敗が多い」）を**言葉で1行**

ボトルネックの判定ロジックは単純でよい（需要が最も高い区画、失敗率が閾値超え、など）。**言葉で出すことが重要。**

#### 受け入れ基準

- オーバーレイ4種が切り替えられ、既定はオフ
- 建物をタップすると数字と「その理由」が出る
- 需要バーをタップすると何で決まっているかが言葉で出る
- 街のサマリでボトルネックが1行で分かる
- **文字列はすべて `ja.ts` 経由**

### W4: 交通 — 行って、帰ってくる

**担当ファイル**: `src/sim/traffic/`, `src/sim/types.ts`（Vehicle型）, `src/render/gameScene.ts` の車描画部分

**注意**: `gameScene.ts` は W2 も触る。**W2 と W4 は同じ wave に入れず、W2 → W4 の順に統合する**（§5参照）。

#### 背景

オーナーの指摘: 「車が往復等がなく、行くのみだから分かりづらい」「目的地についたらすぐ消えてしまうから、建物の入口に入るアニメーション的なものを追加してほしい」

現状: `spawnPeopleTrips` が片道の経路を作り、`arrive()` で車が即座に消える。街の営みとして読めない。

#### やること

**4-1. 往復トリップ**

車は目的地に着いたら、**しばらく滞在してから出発地へ帰る**。

- `Vehicle` に往路/復路の区別と滞在の終了tickを持たせる
- **復路の経路は往路を反転して使う。A* を再実行しない**
  - 理由: 経路探索は1tickあたりの回数に上限を設けてある（性能予算のため）。復路でもう一度走らせると実質2倍になり、予算 5ms/tick を超える危険がある
  - 混雑が変わっても往路の経路を使うのは許容する（実際の通勤も同じ道を帰ることが多い）
- 滞在時間は `balance.ts` に定数を置く（目安 30〜60 tick = 3〜6秒）
- **満足度の加算は往路の到着時に1回だけ**（往復で二重に加算しない）
- 帰宅（復路の到着）で車は消える

**4-1-a. タイムアウトを脚（leg）ごとに計り直す — これを忘れると街が死ぬ**

現在のタイムアウト判定は `state.tick - v.purpose.startedTick > TRAFFIC.TRIP_TIMEOUT (=300)`
（`src/sim/traffic/index.ts` の `moveVehicles`）で、**往路の出発からの通算**で計っている。

往復にすると、往路（渋滞込みで100〜200tick）+ 滞在（30〜60tick）+ 復路（同程度）で
**通算300tickを平然と超える**。超えた車は `timeout()` に落ち、満足度 −4 と `failedToday` が計上される。
つまり**普通に往復できた車が、片っ端から「失敗」として記録される**。

その先で何が起きるか:

1. `failedLastDay / tripsLastDay` = `recentTripFailRate` が跳ね上がる
2. R需要が `DEMAND.R_TRIP_FAIL_PENALTY (=100) × failRate` で最大 −100 される
3. 需要が負に張り付き、入居が止まる。同時に満足度が下がり続けて退去が始まる

**これは M2 で実際に街を停止させた5つの数式バグと同じ構造**（`docs/handoff-2026-07-30.md`「実装書の数式を実測で修正した」）。
仕様の文面が「到着したら消える」前提のまま、片道を往復に変えると成立しなくなる箇所。

対応:

- `Vehicle` に `legStartedTick: number` を持たせ、**往路の出発時と復路の出発時にそれぞれ現在tickを入れる**
- タイムアウト判定は `state.tick - v.legStartedTick > TRAFFIC.TRIP_TIMEOUT` に変える
- **滞在中は一切計時しない**（滞在は渋滞ではないので、遅延として罰する対象ではない）
- `purpose.startedTick` は統計用に残してよいが、**判定には使わない**

**4-1-b. 往復1回を「1トリップ」として数える**

`totalTrips` / `tripsToday` は spawn 時に1回だけ加算されている（`spawnPeopleTrips`）。
復路の出発でもう一度加算すると、**同じ移動が2回数えられて失敗率の分母が水増しされ**、
需要（§8.1）の値が実質的に変わってしまう。バランス調整をしていないのに街の育ち方が変わるので、
「可読性を上げただけ」というM3の前提が崩れる。

- **復路の出発で `totalTrips` / `tripsToday` を加算しないこと**
- 復路が失敗した（タイムアウト・道路撤去で経路喪失）ときだけ `failedTrips` / `failedToday` を加算する
- **テストで担保する**: 往復が正常に完了したとき `tripsToday` の増分が 1 であること

**4-1-c. 同時走行台数がおよそ倍になる**

滞在＋復路のぶん、1台の寿命が2倍以上になる。spawn 率が同じなら**定常状態の同時台数もおよそ倍**。
`TRAFFIC.MAX_VEHICLES (=1500)` に早く張り付き、超過分の spawn が抑制される
（抑制は失敗に数えないので死のスパイラルは起きない）。ただし1日あたりの成功トリップ数が減るため、
満足度の +1 が日次回帰の ±1 に対して弱くなる。

- **M3 では数値を触らない**（バランス調整は後回しというオーナー判断）。
  代わりに **100日ヘッドレス実行で人口が伸び続けることを受け入れ基準に入れる**（下記）
- もし伸びなくなっていたら、`TRAFFIC.TRIP_RATE_R` を半分にするのが最初の一手だと**引き継ぎに書き残す**
  （調整そのものは M6 のバランス調整で行う）

**4-2. 建物に入る/出る演出**

- 目的地の建物に近づくと、車が**縮んで建物に吸い込まれる**（0.3秒程度）
- 滞在中は車が描かれない
- 出発時は建物から**出てくる**（逆の演出）
- これは描画側で表現する。sim は「いま滞在中か」だけを持てばよい

**4-3. 決定論を保つ**

滞在時間・往復の判定はすべて既存のシード付きRNGか固定値で決める。`Math.random` は使わない。既存の決定論テスト（同一シード・同一操作列で10,000tick後の状態が一致）が通り続けること。

#### 受け入れ基準

- 車が目的地に着き、滞在し、出発地へ帰る
- 建物への出入りが見て分かる
- **性能**: 車両1500台で 1tick ≤ 5ms を維持（`src/sim/world.bench.test.ts` で計測。現在 2.02ms）
- 既存の決定論テストが緑
- 満足度が往復で二重加算されない（テストで担保）
- **タイムアウトが脚ごとに計られている**（テストで担保: 滞在時間を `TRIP_TIMEOUT` より長くしても
  失敗として記録されないこと）
- **往復1回で `tripsToday` の増分が 1**（テストで担保）
- **100日ヘッドレス実行で人口が伸び続ける**。実装書 §16 の「ヘッドレス長時間」テストに相当する。
  往復化の前後で人口曲線を比べ、**明確に悪化していないこと**を数値で報告する
  （悪化していた場合は原因を特定して報告する。**balance.ts の値は勝手に変えない**）

## 5. 依存関係と進め方

```
Wave 0（直列・1体）:   W0  継ぎ目の整備（overlayLayer / onTap / store / dragShape）
                            ↓
Wave 1（並列・3体）:   W1（編集操作）  W3a（オーバーレイ）  W3b（インスペクタ）
                            ↓
                       ★ ここでオーナーに一度見せる（W3a・W3b の途中でよい）
                            ↓
Wave 2（並列・2体）:   W2（描画の刷新）   W3c（サマリ・撤退可）
                            ↓
Wave 3（直列・1体）:   W4（交通の往復 + 出入り演出）
                            ↓
                       統合 → verifier 検証 → プレイテスト②
```

**この編成は初版から変更した。** 初版は「W1 と W3 は担当ファイルが重ならないので並列可」と
していたが、コードを読み直したところ**重なる**ことが分かった:

| 初版の想定 | 実際 |
|---|---|
| W3 は `src/ui/` と `render/overlay.ts` だけ | インスペクタは**タップ入力（`loop.ts`）と選択状態（`store.ts`）**が必要。両方 W1 の担当ファイル |
| オーバーレイは新規ファイルで完結 | `world` コンテナは `createGameScene` のクロージャ内。**`gameScene.ts` に層と口を開ける**必要がある。W2 の担当ファイル |
| W3 は UI 専業 | 「満足度が上下している理由」「需要の内訳」は**sim に記録・公開が無い**（§4 の W3b 参照） |

そのまま並列発注すると、2体が同じファイルを書き換えて片方の成果を捨てることになる。
W0 で継ぎ目だけ先に通すことで、この衝突が構造的に消える。

**根拠のある前例**: P0 で「比較したい軸以外を共通化せずに3方式を並列発注し、3人が別々の地形生成を
実装した」という失敗をしている（memory-vault の `projects/machiscape.md`）。
**親が発注前に固定すべき契約の範囲を見誤ると、並列化の利益が手戻りで消える。** W0 はその対策。

### 直列にしなければならない箇所

- **W0 → 全部**（継ぎ目が無いと他が始められない）
- **W2 → W4**（どちらも `gameScene.ts` の車描画を触る。W2 がカプセル型にした後で W4 が出入り演出を足す）

### 委譲の方針

- **根幹の設計判断を含むもの（W3a・W3b・W4）は Opus に委譲する。** 情報設計と交通モデルはゲームの手応えに直結する
- 仕様が確定していて機械的なもの（**W0**・W1・W2・W3c）は Sonnet でよい。
  W0 は「機能を足さない」ことが最重要なので、むしろ余計な創意が入らない方がよい
- 各パッケージのブリーフには、この文書の該当節をそのまま渡せば足りるように書いてある。
  **加えて §4 冒頭のファイル所有権の表を必ず渡す**（表に無いファイルを触らせないため）
- 長時間作業になる場合は**途中でもコミットさせる**（セッション上限で中断されても成果が残る）

## 6. 検証方法

各パッケージ完了時:

1. `pnpm typecheck` / `pnpm lint` / `pnpm test` / `pnpm build` を**終了コードで**確認（`echo $?`。パイプで tail すると終了コードが隠れる）
2. `pnpm dev` を起動し、**ヘッドレスブラウザ（Playwright）で実際に操作**してスクリーンショットを撮る
   - WebGL のcanvasは `drawImage` で読むと真っ黒になる。判定は必ず `page.screenshot()` の PNG をデコードして行う
   - ヘッドレスの WebGL は `--use-gl=swiftshader --enable-unsafe-swiftshader --no-sandbox` が必要
   - **ヘッドレスのFPSは13〜21しか出ない。性能評価には使えない**（描画されているかの確認のみ）
3. 性能は `src/sim/*.bench.test.ts` の実測値をログで確認

全パッケージ統合後:

4. 会話を知らない verifier に検証を委譲する（自己批評より欠陥が見つかる）
5. **オーナーのプレイテスト②**

## 7. リスクと撤退条件

プリモーテム（「この計画は失敗した」と仮定したときの死因）:

| 死因 | 早期警報 | 回避策 |

| **往復トリップが街を殺す**（最も可能性が高い） | 実装後に `failedLastDay` が跳ね上がる／人口が伸びなくなる | タイムアウトを脚ごとに計り直す・復路で `tripsToday` を二重計上しない（§4 W4-1-a/b に設計として織り込み済み）。受け入れ基準に100日ヘッドレスでの人口曲線を入れた |

| **並列発注したagentが同じファイルを書き換える** | 2体の成果がコンフリクトする／片方を捨てることになる | W0 で継ぎ目を先に通し、§4 冒頭のファイル所有権の表を全ブリーフに添付する |
| **往復トリップで性能予算を超える** | ベンチが 5ms/tick に近づく | 復路は往路の反転で A* を追加実行しない（設計に織り込み済み）。それでも超えるなら滞在時間を延ばして同時走行台数を減らす |
| **情報を足したせいで余計に分かりにくくなる** | 画面がごちゃつく／オーナーが「うるさい」と言う | オーバーレイは同時1つ・既定オフ。インスペクタはタップ時のみ。**足すより「既定で静か」を優先する** |

これを落としても M3 の目的は達成できる。逆に W0・W3a・W3b・W4-1-a は落とせない。

## 10. この計画の弱いところ（正直に）

**W3（情報設計）の工数見積りが最も当てにならない。** 「分かりやすい」は作ってみないと判定できず、
オーナーに見せて作り直しになる可能性が高い。だから W3 を最初に着手し、
途中で一度見せる段取りにしてある。それでも1回で決まらない前提でいるべき。

また、**#6「発展が分かりやすい」への答えが W2-3（建物の見た目）と W3（情報表示）に分散している。**
どちらが効いたのか切り分けにくい。プレイテスト②では「建物を見て分かったか」「パネルを見て分かったか」を
分けて聞くとよい。

**改訂版で最も弱いのは W0 の見積り。** 「継ぎ目だけを入れる小さな作業」と書いたが、
実測ではなく類推でしかない。`GameScene.render` の引数を `World` に変える波及が
思ったより広ければ（描画テストが無いので静かに壊れる可能性がある）、W0 が W1 並の規模になる。
**W0 が長引くようなら、並列化をやめて1体の直列実行（§11 の案C）に切り替える判断をすること。**

### 計画の想定が外れたところ（次に活かす）

1. **「W1 と W3 は並列可」は誤りだった**（§5 で訂正済み）。加えて**発注直前にさらに3つの共有点が見つかった**:
   UIコンポーネントのマウント位置（`Hud.tsx`）/ `OverlayMode` の置き場所（`ui` に置くと依存方向に反する）/
   インスペクタが `GameState` を読む手段（storeにstateを載せない設計だったため口が無かった）。
   → **契約は「発注直前にもう一度洗い出す」。計画時点の洗い出しでは足りない**
2. **subagent の worktree がデフォルトブランチ起点で作られ、W0 のコミットを含まなかった**。
   3体すべてが古いベースで開始し、各自 `git merge main` で復旧した。
   → ブリーフに「着手前にベースを確認し、含まなければ merge せよ」を必ず書く
3. **満足度の色は実機を見ないと決められなかった。** 0〜100を線形に緑→赤へ写すと、平常値50が
   警告色になり**健全な街が一面の警告色**に見えた。退去ライン(30)基準に置き直して解決。
   → 「分かりやすい」は作って見るまで判定できないという §10 の予想どおりだった

### 実装中に見つかった既存バグ（M3 のスコープ外だが直した）

- **`validateBridge` が幅1タイルの川を横向きに渡れなかった**（M1からの潜在バグ）。水が1タイルだけの
  区間は `sameX`/`sameY` が同時に成立するのに `sameX` を先に見て常に縦の橋として扱っていた。
  川は幅1〜2タイルで開始チャンクを必ず通るので、**プレイヤーが最初に踏む操作のひとつ**だった
- プレビューと確定結果の不一致2件（別系統モデルのレビューで実測再現）
- StrictMode の二重実行で実行中 World が失われ、**dev環境でだけインスペクタが開かなかった**

### 残っている既知の問題（M3 では直さない）

- **巨大な道路網を一度に敷くと街が停止する。** 建物ゼロの間だけ動く「ダミートリップ」が
  大量の失敗を記録し、`recentTripFailRate` 経由で需要を潰す。**W4 以前から存在する挙動**で、
  W4 の変更を外しても再現することを確認済み。通常のインクリメンタルなプレイでは踏まない。
  M4 以降で扱うか、ダミートリップ自体を廃止するのが筋（建物が建てば不要な機構のため）
- 画面下のUIが4段（ヒント / オーバーレイ / 区画サブ選択 / ツールバー）。スマホ縦での占有が大きい
- インスペクタは「移動ツール中のタップ」でしか開かない。初見で気づけるかは未検証
