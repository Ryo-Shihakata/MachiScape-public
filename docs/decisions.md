## ✅ M2 プレイテスト①の結果（2026-07-30・実施済み）

**判定: 判定不能。** Ryo は実機でプレイした上で、

  何が効いたのか切り分けられなくなる。数値は `src/sim/balance.ts` に集約済みなので後からいつでも触れる

## ⏳ Ryo へ: M3 プレイテスト②のお願い（2026-07-31・実装完了）

```bash
cd ~/dev/projects/MachiScape && git pull && pnpm install && pnpm dev
```

スマホで `http://<tailscale-ip>:5173/`（Tailnet内。自宅LANなら `192.168.x.x`）。

**判定してほしいこと: 「街で何が起きているか分かるか」**

プレイテスト①が「街が読めないので楽しさを判定できない」で終わったので、M3 はその一点だけを直しました。
**面白いかどうかは、まだ聞きません。** まず「読めるか」を見てください。

1. 道路を引く → **区画ツールでドラッグすると矩形で塗れる**（1本ずつなぞらなくてよくなった）
2. 速度を上げて街を育てる。**車が目的地に着いたあと、しばらく滞在して出発地へ帰る**ようになった
3. 画面下の **「渋滞 / 満足度 / 道路アクセス / 区画」** を切り替えてみる（もう一度押すと消える）
4. **「移動」ツールに切り替えて、建物をタップ**する → 満足度と「いまそれが上下している理由」が出る
5. **上のRCI需要バーをタップ**する → その需要が何で決まっているかが言葉で出る

**分けて答えてほしいこと**（#6「発展が分かりやすい」への答えが2か所に分散しているため）:

- **建物を見て**発展の度合いが分かったか（大きさ・濃さ・警告ドット）
- **パネルを見て**分かったか（インスペクタ・需要の内訳）
- **詳細の出し方**（移動ツール中のタップ）に気づけたか。気づけなければUIの作り方を変える
- 画面下のUIが4段（ヒント / オーバーレイ / 区画サブ選択 / ツールバー）ある。**スマホで邪魔ではないか**

**バランス（育つ速さ・数値の大小）はまだ調整していません**（M6でやります）。気になっても今は無視してください。
「読めるようになったか」だけ教えてもらえれば十分です。

## D4: M3 の主題を「街が読める」に変更（2026-07-30・オーナー承認）

- **決定**: 元の M3「施設と進行」を **M4 へ後ろ倒し**し、**M3 を「街が読める」に差し替える**。
  M5「仕上げ」・M6「バランスと公開」も1つずつ繰り下げる。
- **理由**:
  - プレイテスト①が「街が読めないので楽しさを判定できない」で終わった（上記）。
    可読性が前提条件なので、それを先に満たさないと以降のすべての判定ができない
  - M2 の改善要望9点のうち**6点が「街で何が起きているか読み取れない」に集約**された。
    最も要望が集まっている一点に絞る方が、9点を薄く撒くより効く
  - 施設・マイルストーンは「目標と選択を与える」機能であり、
    **街の状態が読めないプレイヤーには選択の判断材料が無い**。順序として後に来るべきだった
- **バランス調整のスコープ**: M3 に含めない（Ryo の指示）。M6 で行う
- **文書への反映**: `docs/plan.md` §7 / `docs/implementation-spec.md` §19 に反映済み。
  実装計画は `docs/m3-plan.md`（M3）と `docs/m4-plan.md`（M4）

## D6: 現実的な車間による容量低下を「正」とする（2026-07-31・オーナー承認）

- **経緯**: T1（車間を物理距離にし、停止線を交差点の手前へ下げた）の結果、
  同じ道路網で支えられる交通量が減り、**150日時点の人口が 616 → 408 に落ちた**
  （タイムアウト率は 13〜30% → 15〜29%）。`TRIP_TIMEOUT` を 300→450 に上げる実験も
  したが人口424どまりで、タイムアウトは原因ではなく**容量低下そのもの**と確認した。
- **決定**: **補償しない。** 車速やタイル容量を上げて以前の規模に戻すことはしない。
- **理由**: 現実的な車間を取れば道路の容量は下がる。それが正しい挙動であり、
  **プレイヤーは道路を増やす・広げることで応じるべき**。それこそが
  「渋滞せず流れる道路網を考えるパズル」という v1 のコアそのもの。
  今後実装する「4車線道路」も、まさに容量を増やす手段としてこの判断と噛み合う。
- **注意**: 以後のマイルストーンで容量制約を足すたびに、
  **タイムアウト率・平均/p90所要時間・人口**を実測して記録すること
  （設計レビューの最大の懸念。積み重なると街が崩壊しうる）。

## D7: 1棟が同時に出せる車は1台まで（2026-08-01・オーナー要望）

- **経緯**: オーナーから「発展段階にかかわらず車の台数が多すぎる」「発展速度が遅い」の2点。
  実測すると**同じ1つの原因**だった。画面上の車の数は「発生率 × 1台の生存時間」で決まるが、
  生存時間は渋滞するほど延びるので、
  `混む → 1台が長く居座る → 車が増える → もっと混む` という**正のフィードバックに歯止めが無かった**。
  実測: 住宅31棟に対し路上に131台（1棟あたり2〜2.6台）、失敗率20%、人口464で頭打ち。
- **決定**: `TRAFFIC.MAX_ACTIVE_TRIPS_PER_BUILDING = 1`。
  1軒から出た車が帰るまで、その家は次の車を出さない。あわせて
  `MOVE_IN.DEMAND_PER_MOVE_IN` を 6 → 4（塗った区画が埋まる速さ）。
- **実測（同一シナリオ・30×30・道路は横4/縦5タイル間隔）**:

  | | 変更前 | 上限のみ | 上限＋入居4 |
  |---|---|---|---|
  | 5日 | 56人 / 7台 | 112人 / 3台 | 392人 / 20台 |
  | 30日 | 432人 / 109台 | 328人 / 15台 | 1216人 / 91台 |
  | 150日 | 464人 / 131台 | 1704人 / 106台 | 1872人 / 133台 |

- **意味**: 人口の頭打ちは需要式ではなく**この暴走が原因だった**。D6 で「容量が減るのは正しい」と
  決めたが、容量が減ること自体は正しくても、**容量を超えた分が路上に溜まり続ける**のは間違いだった。
  上限は溜まった分を「まだ出発していない需要」として建物側に押し戻す背圧として働く。
- **副次的な効果**: 車の数が入居棟数に比例するので、**発展段階と画面の密度が一致する**。
  序盤の街に100台が湧く見た目の破綻が消えた。
- **残る性質**: 上限に達している間の需要は消えるのではなく待つだけなので、
  道路を直せばその日のうちに流量が戻る。

## D8: 資金不足の編集操作はすべて「全か無か」（2026-08-01・オーナー指示）

- **経緯**: M3 の矩形ドラッグ導入時、合計費用が残高を超えやすいことへの対処として、
  `buildRoad` / `upgradeRoad` / `paintZone` / `demolishArea` は走査順に払えるところまで
  部分適用する方針を意図的に採用した。プレビューも同じ走査順で途中から赤にし、
  実結果との一致を優先していた。`downgradeRoad` だけは既に全か無かだった。
- **決定**: 上記4操作を `downgradeRoad` と同じ**全か無か**へ変更する。対象全体の費用を
  操作前に合算し、残高不足なら `OpResult` に理由を返して1タイルも変更しない。
  プレビューも資金判定については対象全体を緑または赤に揃える。`demolishArea` は道路撤去費が
  足りない場合、無料の区画・建物だけを先に消さず、矩形全体を変更しない。
- **理由**: 1回のドラッグはプレイヤーにとって1つの意図であり、残高によって途中までだけ
  実行されると、完成形と費用を予測しにくい。操作前に成功・失敗を明示し、失敗時に街を
  変えない方が、プレビューと操作結果の対応が単純で一貫する。部分適用は不具合ではなく
  過去の意図的な判断だったが、オーナー指示により操作の予測可能性を優先して転換した。

## D5: M4 の主題変更と「弱い動的迂回」（2026-07-31・オーナー承認）

- **経緯**: M3 完了後にオーナーから5要望（交差点の見た目 / ルート選定 / 建物の出入り / まちづくりへの焦点 / 道路以外の手段）。
  別系統モデル（**GPT-5, reasoning effort=high**）に設計レビューを依頼し、その推奨をオーナーが採用した。
- **決定**:
  1. **M4 の主題を「施設と進行」から「交通が見える・反応する」へ変更**。施設・進行は M5 へ後ろ倒し
  2. **交差点は描画だけ直す。信号は入れない**（信号は「交差点が変に見える」問題の解ではない。v1での手動信号は不採用）
  3. **動的迂回は「弱め」**（一部の車が遅れて移る程度）
  4. **鉄道・バスは v2 のまま**（受け口の型だけ v1 に用意済み）
  5. **施設は公園・学校・病院の3種だけの垂直スライス**（5種一括は不採用）
- **最も重い判断の理由（3について）**:
  > 動的な迂回が賢すぎると、**ゲームがプレイヤーの代わりに渋滞を解いてしまう**。
  > 悪い道路網でも車が勝手に最適に流れるなら、「渋滞せず流れる道路網を考えるパズル」という v1 のコアが消える。

  したがって作るのは「完全回避AI」ではなく「**明らかに悪い経路にはまった車の一部が、遅れて別の道へ移る**」程度。
  再探索の間隔・最低改善率・クールダウンは**難易度そのもの**なので `balance.ts` で調整可能にする。
- **5について**: 5種一括で作ると「置く場所を考える楽しさ」が生まれるかを検証せずに実装することになる。
  3種で垂直スライスを作り、**先にオーナーが判定してから**残りを作る。
- **文書への反映**: `docs/plan.md` §7、`docs/m4-plan.md` §0

## D2: 道路を引く操作（2026-07-29）

- **決定**: ドラッグ中は指の軌跡ではなく「**開始タイルから現在位置までの直線**」を常に表示し、
  指を離した瞬間に確定する。直線は**水平・垂直・45度**にスナップする。
- **理由**:
  - 指の軌跡をなぞる方式は、線が震えたり行き過ぎたりして狙った道が引きにくい。直線を引き直す方式なら、
    行き過ぎても指を戻せば線も戻る。
  - L字（2辺）を1ドラッグで引く案もあるが、まず直線で操作感を確かめる。必要なら後から足せる。
- **実装書への反映**: §12.3 に反映済み

## D3: 道路を8方向接続にする（2026-07-29・オーナー指示）

- **決定**: 道路グラフの隣接を**4方向から8方向（斜めを含む）に変更**する。
- **経緯**: D2 の当初案では「斜めのタイル列は角でしか接せず、4方向接続では道路として繋がらない」
  という理由で45度を見送っていた。オーナーの指示により、斜めを引けること自体を要件とし、
  グラフ側を8方向に変更して斜めが実際に機能するようにした。
- **波及**:
  - 経路探索の**斜め移動コストは √2**（1にすると不自然に斜めを選ぶ）
  - ヒューリスティックはマンハッタン距離では過大評価になり最適性が崩れるため、
    **オクタイル距離**に変更
  - 描画はタイル中心どうしを太線で結ぶ方式にし、直交・斜め・交差を同じ仕組みで表現
  - 区画の道路アクセス判定（§8.2）はマンハッタン距離のまま（4方向とは独立の概念なので影響なし）
- **検証**: 斜めの道を1本だけ引いた状態で車50台が走行することを実機ブラウザで確認
  （4方向のままなら経路が見つからず0台になる）

### 試し方

dev-vm で開発サーバを起動する:

```bash
cd ~/dev/projects/MachiScape && pnpm dev
```

スマホのブラウザで以下を開く（同じ Tailnet にいること。dev-vm の Tailscale IP は `<tailscale-ip>`）:

| 方式 | URL |
|------|-----|
| グリッド | http://<tailscale-ip>:5173/proto/grid/ |
| 自由曲線 | http://<tailscale-ip>:5173/proto/spline/ |

1. 道を引くのが気持ちよいか（意図した線が一発で引けるか）
2. 誤操作の起きにくさ（パンとの取り違え、行き過ぎ、引き直しの手間）
3. 見た目が MachiScape のミニマルな方向性に合うか
4. スマホでの指の届きやすさ・視認性
