## 0. 本書の使い方・普遍ルール

- **Tunable**: `(T)` 印の数値はすべて `src/sim/balance.ts` に定数として置く仮の初期値。ゲームの面白さはプレイテストで決まるため、値そのものは仕様ではない。**コード中に数値を直書きしない**
- **決定論**: `src/sim/` 配下は `Math.random` / `Date` / `performance` / DOM / Pixi / React を import しない。乱数はシムが持つシード付きRNGのみ。CIの決定論テストで担保する
- **拡張前提**: 区画タイプ・施設・交通手段は将来追加される（§20）。switch文の網羅ではなくマスターテーブル（Def型の配列）で駆動する
- **i18n**: ユーザー向け文字列はすべて `src/i18n/ja.ts` のキー経由。コンポーネントに日本語を直書きしない
- **やらないこと**: §20「v2以降」に列挙された機能は、フックの用意（型・データ形式）までで実装しない

## 2. アーキテクチャ

### 2.1 ループ構成

- シミュ: 固定タイムステップ **10 tick/秒**（dt=100ms）。描画: requestAnimationFrame で車両位置を線形補間
- 速度制御: ポーズ(0)/1x/2x/3x。倍速はフレームあたりのtick消化数を変える（dtは不変）
- ゲーム内時間: **1日 = 600 tick**（1xで実時間60秒）(T)。日付カウンタのみ持つ（時刻・曜日・昼夜はv1なし）
- ポーズ中も建設操作は可能（BuildOpは即時にstateへ適用される）

### 2.2 状態と操作

```ts
// tickごと: simState = advance(simState, 1)
// 建設操作: simState = applyOp(simState, op)   // op: BuildOp（§12.4）
```

- `GameState` は直列化可能なプレーンオブジェクト（クラス・関数・Map/Setを含めない。Mapが必要な箇所はRecordか配列+索引で持つ）
- Undo: `BuildOp` の逆操作をセッション内スタックに積む（上限 50 (T)。セーブには含めない）
  - 対象: 道路・区画・施設の各操作。**`buyDistrict` はUndo不可**（実行時にスタックをクリアしない。単にpushしない）
  - Undoの実行は通常の `applyOp` として検証を通す。tick進行で状態が変わり検証に落ちる場合（例: 塗り直そうとした区画に建物が建った）はUndo失敗をトーストで表示する
  - `eraseZone` のUndoは区画の塗りのみ復元し、消えた建物は戻らない（§12.4）
- Web Worker 化はv1では**しない**が、`advance`/`applyOp` の直列化可能な境界が移行点になる（§17）

## 3. ドメインモデル（型定義の骨子）

```ts
type TileKind = 'plain' | 'water' | 'mountain' | 'forest';
type ZoneType = 'residential' | 'commercial' | 'industrial'; // 追加はZoneDefへ（§20）
type Mode = 'road'; // v2: 'rail' | 'ship' | ... （§20）

type TilePos = { x: number; y: number }; // グローバルタイル座標（整数）。チャンク相対座標は使わない

interface GameState {
  seed: number;            // マップ生成シード（§5のリトライで確定した採用値）
  rngState: number;        // シムRNGの現在状態。新規作成時に seed から決定論的に初期化する（Date等は使わない）
  tick: number;            // 累計tick。day = floor(tick / TICKS_PER_DAY)
  money: number;
  nextId: number;          // building/facility/vehicle 共通の連番採番カウンタ
  grid: Grid;              // 地形・道路・区画・建物の索引（チャンク配列）
  buildings: Building[];
  facilities: Facility[];
  vehicles: Vehicle[];     // transient扱い（セーブに含めない → §13）
  districts: District[];
  progress: Progress;
}

interface District {
  cx: number; cy: number;
  purchased: boolean;      // 開始チャンク(0,0)のみ false（無償）
}

interface Progress {
  achievedMilestones: string[];      // MilestoneDef.id
  tutorialDone: boolean;
  lastDayReport: DayReport;          // HUDの日次内訳表示用
  dayReports: DayReport[];           // 直近 REPORT_HISTORY_DAYS (T=30) 日。v2統計グラフの下地
  totalTrips: number; failedTrips: number; // recentTripFailRate の算出元は直近1日分
}

interface DayReport {
  day: number; taxR: number; taxC: number; taxI: number;
  upkeepRoad: number; upkeepFacility: number; rewards: number;
  popStart: number; popEnd: number;
}

interface Building {
  id: number;
  pos: TilePos;
  zone: ZoneType;
  level: 1;                // v1は常に1。密度レベル用に予約（§20）
  occupied: boolean;       // 入居済みか
  satisfaction: number;    // 0..100
  stock?: number;          // commercialのみ: 商品在庫 0..100
  output?: number;         // industrialのみ: 生産在庫 0..100
}

interface Vehicle {
  id: number;
  kind: 'car' | 'truck';
  mode: Mode;              // v1は常に'road'
  path: TilePos[];         // 経路（タイル列）
  edgeIndex: number;       // 何本目の辺か
  edgeProgress: number;    // 辺内の進捗 0..1
  purpose: Trip;           // 出発元building/施設・目的地・出発tick
}

interface Facility {
  id: number; defId: string; pos: TilePos; // 効果はFacilityDef（§10）参照
}
```

- `Grid` はチャンク（32×32）ごとの `Uint8Array` 群（terrain / road / zone）+ `buildingIndex: Record<posKey, buildingId>` + `facilityIndex: Record<posKey, facilityId>`（footprintの全占有タイルを登録。§12.4の重複検証はこの2索引+road/zone配列で行う）。直列化は §13
- 道路タイルの接続はグリッド近傍から都度導出し、**経路探索用グラフはキャッシュ**（道路の建設/撤去で無効化→遅延再構築）

## 4. 空間・座標

- 1タイル = 論理1.0。描画は 32px/タイル（ズーム1）。ズーム範囲 0.25〜3 (T)
- チャンク = 32×32タイル。チャンク座標 `(cx, cy)`、開始チャンクは `(0,0)`
- **道路の隣接は8方向**（斜めを含む・D3）。区画の道路アクセス判定など道路以外の近傍は4方向・マンハッタン距離

### W1-2 矩形・直線編集の資金判定（D8）

- `buildRoad` / `upgradeRoad` / `downgradeRoad` / `paintZone` / `demolishArea` は、
  操作対象全体の費用を確定前に合算する。残高不足なら理由付きで操作全体を拒否し、
  **1タイルも変更しない**（全か無か）
- プレビューも同じ合計費用で判定する。資金について途中から赤になる表示はせず、
  対象全体を緑または赤に揃える（地形・道路ランクなど、対象外タイルの赤表示は維持する）
- `demolishArea` で費用がかかるのは道路撤去だけだが、道路撤去費の合計が不足する場合は
  無料の区画・建物も含めて何も撤去しない
- 以前は矩形ドラッグで残高を超えやすいことから、走査順に払える範囲だけを部分適用していた。
  これは当時の意図的な資金不整合対策だったが、D8 で操作の予測可能性を優先して廃止した

## 5. マップ生成（`sim/mapgen/`）

決定論: `hash(seed, cx, cy)` を各チャンクのRNGシードにする（購入順に依存しない）。

タイル種の決定は**優先順位方式**（上書きではなく、タイルごとに以下の順で最初に該当した種になる）:

1. **water**: 川（マップ全体で `seed` から大域的に決まる1〜2本のランダムウォーク・幅1〜2タイル。大域関数 `riverAt(seed, x, y)` で判定し、チャンク生成はそれを参照する）または湖（ノイズ `w > 0.85` (T) の連結領域）
2. **mountain**: 高度バリューノイズ2オクターブで `h > 0.78` (T)
3. **forest**: ノイズ `f > 0.72` (T)
4. **plain**: 上記以外

**保証**: 開始チャンク(0,0)は平地率 ≥ 60%、かつ川が1本通る（満たさなければ内部リトライ: `seed' = seed + attempt`。採用シードを `GameState.seed` に保存）

## 6. 道路と経路探索（`sim/road/`）

- 道路はタイル占有・**8方向自動接続**（斜めを含む。D3 で確定）。水タイルへの道路 = 橋。**橋の直線制約**: 連続する水上の橋タイル列は単一方向（全タイル同x または 同y）で、両端が陸の道路タイルに接続していること。ドラッグプレビュー段階で同じ検証関数により不可表示にする
- 道路撤去時: 撤去タイル上にいる車両は消滅させる（失敗トリップに数えない）。~~残経路に撤去タイルを含む車両は次の辺移行時に再探索し、経路がなければ消滅~~
  - **【2026-07-31 訂正】再探索は実装されていない。** `src/sim/world.ts` の `removeVehiclesOnTiles()` は
    経路に撤去タイルを含む車を**そのまま消している**。仕様の方が実装より先を書いていた
  - 消滅は失敗トリップに数えない（この点は仕様どおり）
- 経路探索: A*（**オクタイル距離**ヒューリスティック。8方向でマンハッタンを使うと過大評価になり最短性が崩れる）。
  辺コスト = `基本コスト × (1 + CONGESTION_WEIGHT (T=2.0) × congestionEMA(tile))`。
  **基本コストは直交1・斜め√2**（斜めを1にすると不自然に斜めばかり選ばれる）
  - `congestionEMA`: タイルごとの混雑度 0..1 の指数移動平均（更新は§7.3）。渋滞を避ける経路選択が自然に起こる
- 経路はspawn時に1回計算。~~再探索は「同一辺に TICKS_STUCK (T=100) tick 滞留」時のみ~~
  - **【2026-07-31 訂正】走行中の再探索は一度も実装されていない。** `isStuck()`（`src/sim/traffic/index.ts`）は
    定義されているだけで**呼び出し箇所がリポジトリ内に存在しない**（`grep -rn "isStuck" src/` の結果は定義の1行のみ）。
    `findPath()` の呼び出しは `src/sim/traffic/trips.ts` の3か所（人流・物流・ダミー）だけで、**すべて spawn 時**
  - つまり**「混雑を見て走行中に迂回する」は現状ゼロ**。辺コストに混雑度が入っているので
    「出発時点の混雑」は経路に反映されるが、走り出した後は固定される
  - この差分の解消は「動的な迂回」として独立したマイルストーンで扱う（`docs/m4-plan.md` 参照）。
    **既存機構の改善ではなく、再探索スケジューラの新設**として見積もること
- グラフキャッシュ: 道路変更でダーティフラグ→次の探索時に再構築。探索は交差点ノード圧縮なし（タイル単位）で開始し、性能不足時のみ最適化する（早すぎる最適化をしない）

## 7. 交通シミュレーション（`sim/traffic/`）

### 7.1 スポーン（人の移動）

- 入居済みresidentialごとにポアソン近似: 毎tick確率 `TRIP_RATE_R (T=0.01)` で車を1台生成（≒6台/日）
- 目的地: 入居済みcommercial 60% / industrial 25% / 施設 15% (T) の重み × 個別重み `attraction / (1 + dist/8)` (T) で抽選
- 経路がない場合は**車を出さず**、その建物に `noPathStrike` を1加算（§8.3の満足度低下へ）

### 7.2 スポーン（物流）

- industrial: 毎日 `PROD_PER_DAY (T=60)` 生産、`output` に蓄積（上限100）
- commercial(入居済): 毎日 `CONSUME_PER_DAY (T=20)` 消費。`stock < 40` (T) になったら配送要求
- 配送要求は商業ごとに `building.id % TICKS_PER_DAY` で決まる時刻に1日1回だけ行い、
  トラックの出発を1日の中へ分散する。スケジュール用のstateは追加しない
- 配送要求は「output ≥ 50 の最寄りindustrial」からトラック1台（積載 `TRUCK_LOAD (T=50)`）
  - **配送要求は1日1回**。毎tick出すと、供給元が無い商業が1日600回失敗を記録して即死する（実測）
  - **供給元が1つも無いのはトリップ失敗に数えない**（道路網の失敗ではないため）。工業不足の罰は
    在庫切れ（§8.3 の `SATISFACTION_OUT_OF_STOCK`）が担う。二重に罰すると工業を建てる前の
    序盤で商業が必ず全滅する
  - 経路がない場合はトリップ失敗として記録し、要求は翌日再試行
- 同日の複数要求は building id 昇順で逐次処理。industrialの `output` は**トラック生成時に減算**し、次の要求は減算後の値で条件を再判定する（同一在庫の二重払い出し・負の在庫を作らない）。タイムアウト消滅したトラックの積荷は失われる

### 7.3 移動と渋滞

- タイルごとの同時在車数 `occ` を管理。速度 `v = VMAX (T=3タイル/秒) × max(0.2, 1 − occ / CAP (T=4))`
- `congestionEMA(tile) ← α=0.05 (T)` で `min(occ/CAP, 1)` を平滑化。オーバーレイ表示（§12.3）と経路コスト（§6）に共用
- 到着した車は消える。**所要tick > TRIP_TIMEOUT (T=300)** で強制消滅し「失敗トリップ」として出発元に記録
- 車両総数上限 `MAX_VEHICLES (T=1500)`: 超過中のスポーンは抑制し、**失敗として数えない**（性能上限が街の衰退を招かないように）

## 8. 需要・発展（`sim/growth/`）

### 8.1 需要バー（RCI、-100..100）

毎日再計算。数式は素朴でよい（すべてTunable）:

- `jobs = 4×occupiedC + 6×occupiedI`、`workers = 8×occupiedR`
- R需要 = `R_BASE + R_JOB_BALANCE_WEIGHT × (jobs/workers − R_JOB_TARGET_RATIO) × 100 − R_TRIP_FAIL_PENALTY×recentTripFailRate`
  - **【2026-07-31 改訂】雇用の項は「差」ではなく「比率」で見る。**
    当初は `0.25×(jobs − workers)` だったが、これだと街が大きくなるほど差そのものが
    大きくなるため、**人口に固定の上限が生まれる**。実際に計算すると、街が自然に
    落ち着く構成（C = pop/16、I = C/2）では `workers − jobs = 4.5×R棟` になり、
    需要が0になるのは `4.5R = 20/0.25 = 80` → **R ≒ 17.8棟 → 人口約142で頭打ち**。
    実測でも112〜152で成長が止まり、オーナーから「152人から増えない」と報告された。
    マイルストーンは人口5000まで続く設計（§11）なので、2つ目以降が到達不能だった
  - 比率なら規模に依存しないので、**商業・工業をきちんと足せば伸び続ける**。
    成長を止めるのは「産業構成の偏り」と「道路網の失敗率」だけになり、
    「渋滞せず流れる道路網を考えるパズル」という v1 のコアと一致する
  - `workers === 0`（街の立ち上がり）は不均衡なしとみなす。そうしないと比率が0になり、
    最初の1棟すら建たない
- C需要 = `(pop / 16 − occupiedC) × 10`
- I需要 = `(occupiedC × 0.5 − occupiedI) × 10`

`pop = 8 × occupiedR`（1棟=8人 (T)）。
各需要は計算時点で **[-100, 100] にクランプ**してから表示・§8.2の両方に使う。表示は §12.2。

**実測に基づく設計上の注意**（当初案から変更した点。変えないと街が成立しない）:

- **C/I 需要は built ではなく occupied と比べる。** built（退去済みを含む）だと店が一度潰れた
  時点で需要が負に固定され、§8.3 の「条件が直れば再入居する」が永久に起きない
  （実測: 商業が全滅して100日戻らなかった）。過剰建設の抑制は §8.2 の
  「空き物件を新築より先に埋める」で担保する
- **`recentTripFailRate` は必ず直近1日で計算する。** 累計比にすると序盤の失敗が永久に需要を
  押し下げ、プレイヤーが道路を直しても街が回復しない（実測: 人口0のまま100日）。
  「直したら良くなる」が伝わることがこのゲームの手応えそのもの
- **R需要の雇用係数は 0.25。** 0.5 だと住宅1棟あたり R需要 −4 で、雇用ゼロの序盤に
  4棟で頭打ちになり、商業・工業が立ち上がる前にデッドロックする

### 8.2 入居

- 区画タイルは「道路タイルからマンハッタン距離 ≤ 2 (T)」なら道路アクセスあり
- `MOVE_IN.INTERVAL_TICKS`（T=60tick）ごとに需要を再計算し、需要が正の区画タイプごとに、
  空き区画タイル（アクセスあり）から
  `需要 / DEMAND_PER_MOVE_IN / (TICKS_PER_DAY / INTERVAL_TICKS)` 棟を抽選で建設・入居する。
  1日あたりの期待棟数は日次実行だったときと同じ。抽選は重み付き
  （基本重み1。施設バフ `growthMul` の範囲内なら乗算 §10）
  - **端数は切り捨てず確率で扱う**。`floor` だと需要が 1〜9 の帯に入ったとき毎日ゼロになり、
    街が永久に止まる（実測: 住宅4棟・商業1棟で停止した）
  - **空き物件（退去済みの建物）を新築より先に埋める**。これが過剰建設の抑制になり、
    同時に §8.3 の再入居を成立させる
- アクセスのない区画タイルには建たない（UIで薄く警告表示 §12.3）

### 8.3 満足度と退去

- 満足度 50 スタート。トリップ成功 +1、失敗（タイムアウト/noPathStrike）−4、毎日 50 に向かって ±1 回帰 (T)
- commercialは `stock = 0` の日 −8 (T)
- **3日連続で満足度 < 30 (T) → 退去**（occupied=false、人口減）。区画と建物は残り、条件が直れば再入居する
- これがv1唯一のペナルティ。破産・ゲームオーバーは存在しない

## 9. 経済（`sim/economy/`）

毎日精算。初期資金 `START_MONEY (T=2000)`。

| 項目 | 値 (すべてT) |
|------|------|
| 税収 | R: 2/日・C: 3/日（stock=0の日は半額）・I: 3/日 ×入居棟 |
| 道路建設 | 10/タイル。橋 50/タイル。撤去 2（返金なし） |
| 森の伐採 | 5/タイル（区画・道路設置時に自動加算） |
| 区画の塗り | 2/タイル。解除 無料 |
| 道路維持費 | 0.05/タイル/日 |
| 施設 | FacilityDef個別（§10）。建設費 + 維持費/日 |
| エリア購入 | `1000 × 1.5^(有償購入済みチャンク数)`（開始チャンクは数えない。初回=1000） |

- 残高が費用に満たない操作はUIで無効化（マイナス残高は発生しない）
- 内部整合: 税収・支出の日次サマリを `progress.lastDayReport` に残しHUDで内訳表示

## 10. ユニーク施設（`sim/facility/defs.ts`）

データ駆動。`FacilityDef` の配列に追加すれば施設が増える構造にする。

```ts
interface FacilityDef {
  id: string;
  cost: number; upkeep: number;
  attraction: number;          // 0なら行き先にならない
  buff?: { radius: number; satisfactionFloor?: number; growthMul?: number };
  unlock: { milestoneId: string } | 'start';
  footprint: 1 | 4;            // 占有タイル数（1=1x1, 4=2x2）。posは左上タイルを指す
}
```

初期セット（数値はすべてT）:

| id | 名称 | cost/upkeep | attraction | バフ | 解放 | 占有 |
|----|------|------|------|------|------|------|
| park | 公園 | 200 / 1 | 2 | r5: 満足度下限+10 | 開始時 | 1x1 |
| school | 学校 | 500 / 3 | 6 | r8: 入居抽選の重み×1.2 | pop100 | 1x1 |
| hospital | 病院 | 800 / 5 | 4 | r10: 退去条件を4日連続に延長 | pop300 | 1x1 |
| cityhall | 市役所 | 1200 / 8 | 5 | 全域: 税収×1.05 | pop500 | 2x2 |
| stadium | スタジアム | 0（報酬・無料設置） / 10 | 20 | — | pop1000 | 2x2 |

- 配置条件: 平地（森は伐採費）・道路アクセス ≤ 2（2x2はいずれか1タイルが満たせばよい）。撤去可（建設費の25%返金 (T)）
- バフの重複は同種非累積・異種累積

## 12. 画面・UI仕様（モバイル優先）

### 12.1 画面一覧

1. **タイトル**: 続きから / 新しく始める（シード入力は「詳細」に折り畳み）/ 設定
2. **ゲーム画面**: 下記
3. **設定モーダル**: テーマ（ライト/ダーク/システム）・SE音量・セーブ管理（スロット/エクスポート/インポート）・クレジット
4. **マイルストーンパネル**: 達成状況と次目標

### 12.2 ゲーム画面レイアウト（スマホ縦）

- 上部バー: 資金 / 人口 / 日付 / 速度（ポーズ・1x・2x・3x。**3xはpop1000マイルストーンで解放** §11。未解放時はロック表示）。タップで日次収支の内訳ポップ
- RCI需要バー: 上部バー直下に小さく常時表示
- 下部ツールバー（横スクロール可）: パン / 道路 / 区画（住・商・工サブ選択）/ 施設（解放済み一覧）/ 撤去 / 情報オーバーレイ / Undo
- マイルストーン進捗: 下部ツールバー上に細いプログレスバー
- PC: 同レイアウトで、ショートカット（1〜7でツール、Space=ポーズ、+/-=ズーム）とホイールズームを追加

### 12.3 操作（タッチ）

- **ツール方式**: 選択中ツールがドラッグの意味を決める。パンツール時=ドラッグでパン
- **道路の引き方（D1/D2 で確定・Mini Motorways 準拠）**: ドラッグ中は指の軌跡ではなく
  「**開始タイルから現在位置までの直線**」を常に表示し、指を離した瞬間に確定する。
  直線は**水平・垂直・45度**にスナップする。行き過ぎても指を戻せば線も戻る。
  費用と残高不足は確定前にプレビュー上で示す
  - 45度が成立するのは道路グラフを8方向接続にしているため（§6・D3）
  - プレビューは確定後の道路と**同じ見た目**（繋がった1本の道）で描く。仕上がりが事前に分かるようにするため
- 2本指は常にパン/ピンチズーム（ツール無関係）
- 区画: ドラッグで矩形塗り。撤去: タップ/ドラッグ
- 情報オーバーレイ: 渋滞ヒートマップ / 区画色分け / 満足度 / 道路アクセス警告 の切替
- 誤操作対策: 確定前プレビューとUndoで担保（確認ダイアログは出さない）

### 12.4 BuildOp（UI→simの操作境界）

```ts
type BuildOp =
  | { kind: 'buildRoad'; tiles: TilePos[] }
  | { kind: 'demolishRoad'; tiles: TilePos[] }
  | { kind: 'paintZone'; zone: ZoneType; tiles: TilePos[] }
  | { kind: 'eraseZone'; tiles: TilePos[] }
  | { kind: 'placeFacility'; defId: string; pos: TilePos }
  | { kind: 'removeFacility'; id: number }
  | { kind: 'buyDistrict'; cx: number; cy: number };
```

`applyOp` は検証（残高・地形・重複＝road/zone配列+buildingIndex+facilityIndex）を行い、失敗理由を返す。UIは事前チェックにも同じ検証関数を使う（二重実装しない）。

- `eraseZone`: タイルに建物がある場合は**建物ごと撤去**（強制退去・人口減・返金なし）した上で区画を解除する。UIのプレビューで対象建物数を表示する
- `demolishRoad` の車両への影響は §6 参照

### 12.5 初回チュートリアル

初プレイ時のみ、3ステップのオーバーレイ（道路を引く→住宅区画を塗る→商業を塗って車が走るのを見る）。
スキップ可。進行フラグはセーブに保存。

## 13. セーブ/ロード（`save/`）

- IndexedDB（`idb` パッケージ）。DB `machiscape`、store `saves`
- スロット: `auto`（毎ゲーム日終了時に上書き）+ 手動3スロット + JSONエクスポート/インポート（v2クラウド同期の下地）
- 形式: `SaveGame = { schemaVersion, savedAt, name, state: GameState }`。`schemaVersion` は SaveGame にのみ持つ（GameStateには持たせない）
  - `grid` の `Uint8Array` は base64 化。`vehicles` は**保存しない**（ロード時に空で再開。走行中の車は失われるが失敗にも数えない）
- 移行: `migrations: Record<number, (old) => new>` を v1 から用意（空でよい）。ロード時に `schemaVersion` を順に適用
- 破損セーブはロード失敗を明示し、新規開始かインポートを促す（無言でリセットしない）

## 14. 効果音（`audio/sfx.ts`）

Web Audio APIで合成（音声アセットなし）。イベント: 道路確定 / 区画塗り / 建物入居（ポップ音）/
施設設置 / マイルストーン達成（短いチャイム）/ 操作エラー。音量設定と完全ミュートを設定に持つ。
モバイルの自動再生制限のため、初回タップで `AudioContext.resume()` する。

## 15. i18n（`i18n/`）

- `ja.ts` に全文字列（ネストしたconstオブジェクト、キーは英語）。`t('toolbar.road')` 形式
- 数値・日付のフォーマットも関数化。v2で `en.ts` を追加するだけで切替可能な構造にする（言語切替UIはv1では出さない）

## 16. テスト計画（Vitest）

| 対象 | テスト |
|------|--------|
| 決定論 | 同一シード・同一操作列で10,000tick後の `hash(state)` が一致（CIの回帰対象） |
| mapgen | 開始チャンク保証（平地率・川）。同一シードで同一チャンク。購入順に依存しない |
| road/A* | 最短経路・橋経由・経路なし判定・混雑コストで迂回すること |
| traffic | 渋滞で速度低下・タイムアウト失敗・車両上限時に失敗計上しない |
| growth | 需要式・入居・退去（3日連続<30）・再入居 |
| economy | 日次精算の整合（残高が負にならない・内訳合計=増減）|
| save | round-trip（保存→復元→hash一致、vehicles除く）・base64・移行の枠組み |
| ヘッドレス長時間 | 代表的な操作スクリプトで100日実行し、人口・資金が発散/全滅しない範囲に収まる（バランス崩壊の検知） |

UIはv1では手動テスト（プレイテストゲートで担保）。E2Eは公開後に検討。

## 17. パフォーマンス予算

- 対象機: ミッドレンジAndroid（Pixel 6a級）
- 60fps描画 / シミュ1tick ≤ 5ms（3x時=秒30tickでも余裕を残す）/ 規模想定: 建物2,000・車両1,500
- 描画: 地形はチャンクごとRenderTextureにベイク / 道路はGraphicsを変更時のみ再構築 / 車両は単一テクスチャのSprite群（必要ならParticleContainer）/ 建物はテクスチャアトラス化した図形スプライト
- 計測: M0で実機FPS表示（デバッグHUD）を入れ、以後常時確認
- 予算超過時の段階策: ①描画LOD（ズームアウト時に車両を点に）②A*のノード圧縮 ③シミュのWorker移行（§2.2の境界で切る）。**v1では①まで、②③は必要になるまでやらない**

## 20. v2以降に持ち越し（フックの設計指針）

実装しない。ただしv1のコードは以下を壊さない形で書く:

| v2機能 | v1で用意するフック |
|--------|------|
| 鉄道・船・バス等 | `Mode` 型と `Vehicle.mode`。経路探索はモード別ネットワーク（v1は'road'のみ）を引数に取る関数シグネチャにする。**乗換・駅の実装はしない** |
| 区画タイプ追加・密度 | `ZoneDef` テーブル駆動・`Building.level` 予約済み |
| クラウド同期 | セーブのJSONエクスポート形式がそのまま同期ペイロード。`schemaVersion` 移行機構 |
| BGM | `audio/` にSEと分離したチャンネル構造（音量設定を `se` / `bgm` で分けて保存） |
| 英語UI | i18nキー経由の徹底（§15） |
| 統計グラフ | `progress` に日次サマリ履歴を残す（直近30日 (T)。表示UIは作らない） |
| 災害・イベント | なし（フック不要。イベントシステムはv2で設計） |
