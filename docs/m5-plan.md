# M5 計画: 触って気持ちよく、街が読める

オーナーからの15件の指摘をまとめたもの。**M5 は新機能より「操作の正しさ」が主題**で、
入力系のバグ修正を最優先に置く。作り足す機能（分析カテゴリー・流れの可視化）は
そのあとに来る。

指摘の原文と対応の対照は §6。

---

## 1. W1: 入力（最優先・バグ）

### 1-1. 2本目の指がツールのドラッグを「確定」してしまう

**これが「スクロールしただけで設置される」の正体。** 閾値の問題ではなく、確実に起きる。

`src/render/camera.ts` の `onPointerDown` は、2本目のポインタが来たとき
`if (mode === 'tool') handlers.onDragEnd?.(toWorld(last))` を呼ぶ。
`onDragEnd` は `commitDrag`（＝建設の確定）なので、**2本指でスクロールを始めるたびに
1本目が触れた地点へ1タイル建設される**。

- **直し方**: `PointerHandlers` に `onDragCancel?()` を足し、ピンチへ移行するときは
  確定ではなく破棄する。`loop.ts` 側は `dragTiles` を捨ててプレビューを消すだけにする。
- 同じ理由で `pointercancel`（OSがジェスチャを奪ったとき）も破棄に回す。
  今は `endPointer` が確定に流している。

### 1-2. 建設には「意図」を要求する

`pointerdown` の瞬間に `onDragStart` を呼ぶのをやめ、次のどちらかを満たすまで**保留**する。

| 条件 | 解釈 |
|------|------|
| `INPUT.TOOL_SLOP_PX`（**6px**）を超えて動いた | 線を引きたい → ドラッグ建設 |
| `INPUT.TOOL_HOLD_MS`（**90ms**）押し続けた | 1タイル置きたい → タップ建設 |

保留中に指が離れたら**何もしない**。保留中に2本目が来たら破棄（1-1と同じ扱い）。

90ms にする理由: 人が意図して押すタップは概ね 80〜200ms かかる。
画面を擦っただけの接触はそれより短く終わる。**両方に閾値を置くのが要点**で、
移動だけを見るとタップ建設が死に、時間だけを見るとドラッグ開始が遅れて線が欠ける。

### 1-3. タップ判定を指の太さに合わせる

`TAP_SLOP_PX` は 8px。高精細なスマホでは指の腹が触れるだけで簡単に超えるので
**14px** に上げる。これが「開こうとしていないパネルが開く」の一因。

ただし**この指摘の本丸は 3-2**（インスペクタを分析ツール中だけに限る）。
閾値をいくら調整しても、パンしているつもりのタップで情報が開く構造は変わらない。

### 1-4. PC の移動操作

- **中ボタン（スクロールボタン）ドラッグ** — **どのツールでも常にパン**。
  建設ツール中でも地図を動かせる、PC でいちばん素直な逃げ道。
- **左ドラッグ** — 建設ツール以外（パン・分析・交通）ではパン。現状どおり。
- ホイールズームは現状のまま。

### 1-5. 長押し撤去がスマホで効かない

いまは `armLongPress()` が `onDragStart`（＝ツールモードのときだけ来る）でしか呼ばれず、
**パンツールや分析ツールでは長押しが存在しない**。さらに解除条件が
「タイル座標が変わったら」なので、ズームアウト時は数十px動いても解除されず、
逆にズームイン時は指のわずかな揺れで解除される。

- **直し方**:
  - 長押しの武装を `pointerdown` に移し、**どのツールからでも**入れるようにする
  - 解除は**ピクセル距離**（`INPUT.LONG_PRESS_SLOP_PX` = 10px）で判定する
  - 2本目の指が来たら解除（ピンチと競合させない）

## 2. W2: sim（経済・成長・物流）

### 2-1. 資金不足はすべて「全か無か」（方針転換）

いまは `buildRoad` / `upgradeRoad` / `paintZone` / `demolishArea` が
**払えるところまで部分適用**する。これは実装書 §4 W1-2 で「矩形ドラッグで合計費用が
残高を超えるため」に入れた判断だったが、**オーナーの指示で全か無かへ変える**。

- 資金が足りなければ**1タイルも変えず**、トーストで理由を出す
- プレビューは全部緑か全部赤のどちらか（途中から赤にならない）
- `downgradeRoad` は既に全か無かなので、これで4つの op の挙動が揃う

**この変更は `docs/decisions.md` に D8 として記録すること。** 実装書 §4 W1-2 の
記述も併せて改訂する（実装書とコードが食い違ったまま残さない）。

### 2-2. 需要をリアルタイムに反映して建つ

いまの `processMoveIn` は1日1回。600tick（実時間60秒）ごとに `demand / 4` 棟が
**まとめて湧く**ので、区画を塗ってから何も起きない時間が長い。

- `MOVE_IN.INTERVAL_TICKS`（**60tick = 6秒**）ごとに入居処理を回す
- 1回あたりの棟数は `demand / DEMAND_PER_MOVE_IN / (TICKS_PER_DAY / INTERVAL_TICKS)`。
  **1日あたりの期待値は今と同じ**にする（成長速度は D7 で調整済みなので動かさない）
- 端数は既存と同じく確率で扱う（`chance`）
- 需要の再計算（`computeBuildingStats` → `computeDemand`）も同じ間隔で行う

**日次パイプラインの順序を壊さないこと。** 税収・満足度・物流は日次のまま。
入居だけを日次から切り出す。

### 2-3. トラックの出発時刻をばらす

`spawnFreightTrips` は `stepDay` から1日1回呼ばれるので、**全トラックが同じtickに湧く**。

- 商業ごとに1日の中の決定論的なオフセットを持たせる（`building.id` から導く。
  `id % TICKS_PER_DAY` のような剰余でよい。**新しい state を増やさない**）
- 毎tick「自分の番のtickか」を見て、その建物ぶんだけ配送要求を出す
- 「1日1回だけ要求する」という既存の性質は保つ（`trips.ts` の注意書きにある、
  毎tick呼ぶと満足度が即死する件）

## 3. W3: UI 再編

### 3-1. ツールバーの並び

```
パン │ 道路 │ 区画 │ 交通 │ 分析 │        │ 撤去
```

**撤去を右端へ隔離する。** 破壊的な操作が建設系のボタンに紛れていると誤爆する。
間に余白を入れて、指が滑って隣を押す事故も減らす。

### 3-2. 分析ツール（新規・6つ目）

**「情報を見る」を1つのツールに集約する。** これが「開こうとしていない家の情報が開く」の
構造的な解になる——分析ツールを選んでいないとき、タップで情報は**開かない**。

- 分析ツールのサブ行（区画・道路と同じ形）に、見るものを並べる:

  | サブ選択 | 中身 |
  |---------|------|
  | なし | 何も塗らない。タップで建物・車の詳細だけ見る |
  | 渋滞 | 既存 `congestion` |
  | 満足度 | 既存 `satisfaction` |
  | 道路アクセス | 既存 `roadAccess` |
  | 区画 | 既存 `zone` |
  | **流量** | 新規。§4-3 |
  | **経路** | 新規。§4-4 |

- 既存の `OverlayPicker` は**この行に移設して廃止**する。同じものが2か所にある状態を作らない
- 分析ツール中のタップは T6 の選択（車 → 建物 → 何もなし）をそのまま使う
- **分析ツール以外ではインスペクタを開かない。** ツールを切り替えたら選択も消す

### 3-3. 需要バーの表示・非表示

トップバーにトグルを1つ足す。既定は**表示**（今の見え方を変えない）。
状態は `ui/store.ts` に持つ（sim には持たせない。セーブに入れる情報ではない）。

### 3-4. 建物を選んだときに通勤が見える

オーナーの「施設を選択したら、そこに行く車、そこから出た車（通勤関係）が見える」は
**建物ぜんぶ（家・店・工場）の意味**と確認済み。T6 で入った建物トレースがすでにこれに当たる。
M5 では実機で見て足りない部分だけを足す:

- インスペクタに「出発中 N台 / 向かっている M台」だけでなく、**相手先の内訳**を出す
  （例: 「商業(18,3)へ 3台 / 工業(4,20)へ 1台」）
- 分析ツール中に限るので、常時出て邪魔になることはない

## 4. W4: 描画

### 4-1. T字路で信号が浮く

`drawIntersectionMarkers` は交差点の形に関係なく**常に4方向**へ停止線を描いている
（`for (const sign of [-1, 1])` を両軸に対して回す）。T字路では道路の無い側にも線が出る。

- `orthogonalIntersectionAt` は接続数を数える段階で**どの向きに道路があるか**を
  既に知っている。それを `OrthogonalIntersection` に載せて描画まで運ぶ
- 描画は道路のある向きにだけ停止線を出す
- **sim 側の通行判定は変えない。** 見た目だけの修正であることをテストで担保する

### 4-2. 時々見える黒い細い線

有力な原因は**チャンク境界の枠線**。`redrawWorld` が解放済みチャンクごとに
`rect(ox, oy, CS, CS).stroke({ width: 0.06, color: theme.gridLineStrong, alpha: 0.8 })`
を描いている。32タイルごとに1本なので画面に入ったり入らなかったりし、
「時々見える」「原因不明」という報告と一致する。

- **まず実機のスクリーンショットで確認すること。** 別の原因（タイル間の継ぎ目、
  影レイヤーのブラー端）である可能性も潰す
- 枠線が原因なら、区画の境界を示す意図はあるので消すのではなく、
  **地形と喧嘩しない見え方**（色を地形寄りに、alpha を下げる、破線にする）へ直す
- 継ぎ目が原因なら、隣接タイルを半ピクセル重ねて描く

### 4-3. 流量オーバーレイ（新規）

**「どの道が街の幹線になっているか」を一目で見せる。** 幹線道路をどこに引くべきかの
判断に直結するので、これが分析カテゴリーの主役になる。

- 各道路タイルの**通過台数の移動平均**を持つ（混雑度 `congestion` と同じ EMA の作りを流用。
  混雑度は「いま何台いるか」＝密度、流量は「どれだけ通ったか」＝スループットで別物）
- よく使われる道ほど**明るく・太く**光らせる
- 上限は街ごとに変わるので、**画面内の最大値で正規化する**。
  固定の絶対値だと序盤は真っ暗、終盤は全部真っ白になる

### 4-4. 経路オーバーレイ（新規）

いま走っている全車の経路を半透明で重ね描きする。同じ道を通る車が多いほど濃くなる
（加算合成にすれば自然にそうなる）。

- 車が増えると線の束になるので、**1台あたりの alpha を低く**する
- 描き直しは毎フレームではなく `ANALYSIS.ROUTE_REFRESH_TICKS` ごと
- 1,500台 × 経路30タイルを毎フレーム引くのは論外。**上限台数を設けて間引く**

流量（4-3）と経路（4-4）は似て非なるもので、両方あることに意味がある。
流量は「道の実績」、経路は「いまの人の流れ」を見せる。

## 5. 作業の分割と担当

| 波 | 内容 | 主に触るファイル |
|----|------|------------------|
| W1 | 入力（§1） | `src/render/camera.ts`、`src/game/loop.ts` の入力部 |
| W2 | sim（§2） | `src/sim/world.ts`、`src/sim/growth/`、`src/sim/traffic/trips.ts` |
| W3 | UI 再編（§3） | `src/ui/**`、`src/i18n/ja.ts` |
| W4 | 描画（§4） | `src/render/**`、`src/sim/road/intersection.ts` |

`src/sim/balance.ts` の新しい定数（`INPUT` / `ANALYSIS` / `MOVE_IN.INTERVAL_TICKS`）は
**着手前に親がまとめて追加する**。4つの波が同じファイルの同じ場所を取り合わないため。

`src/game/loop.ts` は W1・W3・W4 が触るが、触る関数が違う（入力ハンドラ / HUD とツール配線 /
交差点マーカーの構築）。**担当外の関数には触らないこと。**
