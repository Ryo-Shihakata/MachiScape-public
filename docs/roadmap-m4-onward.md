## 0. この文書の前提

**M3 の主題変更は 2026-07-30 にオーナー承認済み。** 経緯:

元の計画（`docs/plan.md` §7）では M3 = 「施設と進行」だった。しかし M2 完成後のプレイテスト①で
オーナーが「**街が読めないので、楽しいかどうかを判定できなかった**」と報告し、
改善要望9点のうち6点も「街で何が起きているか読み取れない」に集約されたため、
M3 を「街が読める」に差し替え、施設と進行を M4 へ後ろ倒しした。

`docs/plan.md` §7 と `docs/implementation-spec.md` §19 のマイルストーン表は**反映済み**。

| ID | 内容 | 状態 |
|---|---|---|
| M0〜M2 | 雛形 / 空間モデル決定 / シミュの芯 / 街の発展 | 完了 |
| M3 | 街が読める | 計画済み → `docs/m3-plan.md` |
| **M4** | **施設と進行** | **ファイル単位の実装計画あり → `docs/m4-plan.md`**（本文書の §2 は概要） |
| **M5** | **仕上げ** | 本文書（ロードマップのみ） |
| **M6** | **バランスと公開** | 本文書（ロードマップのみ） |

**M4 に着手する人は本文書ではなく `docs/m4-plan.md` を読むこと。** 本文書 §2 は全体像を掴むための概要で、
既存フックの場所・バフの適用箇所・目的地の一般化といった実装の要点は m4-plan.md にしかない。

**M5・M6 を意図的に詳細化していない理由**: どちらも M3・M4 の結果に強く依存する
（M5 のセーブ形式は M4 の `GameState` が固まってから、M6 のバランス調整はプレイテストの結果から決まる）。
先に詳細化しても作り直しになるため、着手直前に m3-plan.md / m4-plan.md と同じ粒度へ落とす。

## 1. 全体の狙い

M3 までで「街が育ち、その様子が読める」ところまで行く。M4 以降は **v1 として公開できる状態** に持っていく。

- **M4**: プレイヤーに *目標* と *選択* を与える。ここまでで「ゲーム」として成立する
- **M5**: 中断・再開・音・初回体験。ここまでで「製品」として成立する
- **M6**: 面白さの調整と公開。ここで v1 完成

各マイルストーンの終わりに**オーナーの判定**が入る。特に M6 のプレイテストは面白さの最終ゲート。

## 2. M4: 施設と進行

**目的**: エンドレスな街づくりに「次の目標」と「置く場所を考える楽しさ」を与える。

現状（M3 完了時点）は、区画を塗れば街が育つが、**プレイヤーが選ぶことがほとんど無い**。
施設は「どこに置くか」という位置の意思決定を生み、マイルストーンは「次に何を目指すか」を与える。

### W1: ユニーク施設

**担当ファイル**: `src/sim/facility/`（新規）, `src/sim/world.ts`（`applyOp` の施設分岐）, `src/ui/`, `src/render/`

実装書 §10 に仕様が確定している。**データ駆動**（`FacilityDef` の配列に足せば施設が増える）にすること。

```ts
interface FacilityDef {
  id: string;
  cost: number; upkeep: number;
  attraction: number;          // 0なら行き先にならない
  buff?: { radius: number; satisfactionFloor?: number; growthMul?: number };
  unlock: { milestoneId: string } | 'start';
  footprint: 1 | 4;            // 1x1 or 2x2タイル。posは左上
}
```

初期セット5種（数値はすべて `balance.ts` へ。実装書 §10 の表を参照）:

| id | 名称 | 役割 |
|---|---|---|
| park | 公園 | 周囲の満足度に下限を作る |
| school | 学校 | 行き先になる + 周囲の入居を促進 |
| hospital | 病院 | 周囲の退去判定を猶予する |
| cityhall | 市役所 | 全域の税収を増やす（2x2） |
| stadium | スタジアム | 強い行き先（2x2・マイルストーン報酬で無料設置） |

**重要な設計点**:

- 施設は **人流の目的地になる**（`attraction`）。現在の交通は住宅→商業/工業しか行き先が無いので、
  `src/sim/traffic/trips.ts` の `pickDestination` に施設を加える必要がある
- バフの重複は**同種は非累積・異種は累積**（実装書 §10）
- 配置条件は平地（森は伐採費）・道路アクセス2タイル以内。2x2はいずれか1タイルが満たせばよい
- **現在 `applyOp` の `placeFacility` / `removeFacility` は「M3で未実装」と返している。** ここを実装する
- `grid.facilityIndex` に footprint の全占有タイルを登録すること（重複判定に使う）

**受け入れ基準**:
- 5種すべてが置ける・撤去できる（撤去は建設費の25%返金）
- 施設が人流の目的地になっている（車が施設へ向かう）
- バフが実際に効いている（テストで担保: 公園の範囲内で満足度が下限を割らない等）
- 施設を1つ追加するのに `FacilityDef` の配列に1行足すだけで済む

### W2: マイルストーン進行

**担当ファイル**: `src/sim/progress/`（新規）, `src/ui/`

実装書 §11 に仕様が確定している。人口の到達で施設が解放され、報奨金が入る。

| pop | 報奨金 | 解放 |
|---|---|---|
| 100 | 500 | 学校 |
| 300 | 800 | 病院 |
| 500 | 1200 | 市役所・**エリア購入** |
| 1000 | 2000 | スタジアム・3x速度 |
| 2000 | 3000 | （バッジのみ） |
| 5000〜 | 2000ごと繰り返し | （バッジのみ・エンドレス） |

**重要な設計点**:

- 達成判定は**日次**（毎tickやらない）
- 達成時にバナー表示 + 効果音（音は M5 だが、鳴らす場所は M4 で用意しておく）
- `state.progress.achievedMilestones` に記録する（既にフィールドは存在する）
- **3x速度は pop1000 で解放**。それまで速度ボタンをロック表示にする（実装書 §12.2）
- 報奨金は日次レポートの `rewards` に計上する（フィールドは既に存在し、いま常に0）

**受け入れ基準**:
- 人口到達で施設が解放され、報奨金が入る
- 未解放の施設・速度がUIでロックと分かる
- 達成が一度きり（同じマイルストーンで二重に報奨金が出ない）をテストで担保

### W3: エリア拡張

**担当ファイル**: `src/sim/world.ts`（`buyDistrict` は実装済み）, `src/ui/`, `src/render/`

**シミュ側は既に動く**（`applyOp` の `buyDistrict` は実装済み・テスト済み）。**UIが無い**のが残作業。

- 解放済みチャンクに隣接するチャンクを購入できる
- 価格は `1000 × 1.5^(有償購入済み数)`（開始チャンクは数えない）
- pop500 のマイルストーンで解放される

**UIの設計**:
- 解放済みエリアの外側に「購入できる」ことが見て分かる表示（点線の枠 + 価格）
- タップで購入確認 → 購入すると地形が生成されて広がる

**受け入れ基準**:
- 購入UIから隣接チャンクを買える
- 買えない理由（未解放・資金不足・非隣接）が分かる
- 買った直後に地形が見える

### M4 の完了条件

1. W1〜W3 の受け入れ基準を満たす
2. 全ゲート緑（`pnpm typecheck` / `lint` / `test` / `build` が終了コード0）
3. **人口1000まで通しでプレイできる**（ヘッドレスでの自動プレイまたは手動確認）
4. 性能: 車両1500台で 1tick ≤ 5ms を維持

## 3. M5: 仕上げ

**目的**: 中断して再開できる、初めての人が迷わない、公開できる体裁にする。

### W1: セーブ / ロード

**担当ファイル**: `src/save/`（新規）

実装書 §13 に仕様が確定している。**M4 までのどこかで一度は着手しておくと安全**（データ形式が固まってから作ると移行が要る）。

- IndexedDB（`idb` パッケージは導入済み）。DB `machiscape`、store `saves`
- スロット: `auto`（毎ゲーム日終了時に上書き）+ 手動3スロット + JSONエクスポート/インポート
- 形式: `SaveGame = { schemaVersion, savedAt, name, state: GameState }`
  - `grid` の `Uint8Array` は base64 化
  - **`vehicles` は保存しない**（ロード時に空で再開。走行中の車は失われるが失敗にも数えない）
- **移行機構を最初から用意する**: `migrations: Record<number, (old) => new>`。v1 では空でよい
- 破損セーブはロード失敗を明示する。**無言でリセットしない**

**受け入れ基準**: 保存→復元で状態ハッシュが一致（vehicles除く）。移行の枠組みがテストされている。

### W2: タイトル画面と初回チュートリアル

- タイトル: 続きから / 新しく始める（シード入力は「詳細」に折り畳み）/ 設定
- チュートリアル: 初プレイ時のみ3ステップのオーバーレイ
  1. 道路を引く
  2. 住宅区画を塗る
  3. 商業を塗って車が走るのを見る
- スキップ可。進行フラグは `progress.tutorialDone` に保存（フィールドは既に存在する）

### W3: 効果音

**担当ファイル**: `src/audio/`（新規）

- **Web Audio API で合成する。音声アセットは持たない**（実装書 §14）
- イベント: 道路確定 / 区画塗り / 建物入居 / 施設設置 / マイルストーン達成 / 操作エラー
- 音量設定と完全ミュートを設定に持つ
- モバイルの自動再生制限のため、**初回タップで `AudioContext.resume()` する**
- v2 で BGM を足せるよう、音量設定を `se` / `bgm` に分けて保存する（実装書 §20）

### W4: 設定画面とテーマ

- テーマ（ライト / ダーク / システム）・SE音量・セーブ管理・クレジット
- **ダークテーマは `theme.ts` に定義済みだが、切り替えUIが無い**。ここで繋ぐ

### W5: モバイルUIの磨き

M3・M4 で機能が出揃った後の調整。

- セーフエリア（ノッチ・ホームバー）の確認
- タップ領域が最低 44×44 CSS px であること
- 狭い画面（幅360px）で破綻しないこと
- **実機での確認が必須**（ヘッドレスでは操作感が分からない）

### M5 の完了条件

1. 保存 → アプリを閉じる → 再開、が実機で通る
2. 初見の人がチュートリアルだけで道路と区画の操作を理解できる
3. 全ゲート緑

## 4. M6: バランスと公開

**目的**: 面白さを詰めて、遊べる場所に出す。

### W1: バランス調整（**オーナーのプレイテストが主役**）

数値はすべて `src/sim/balance.ts` に集約してある。**コードを書き換えずに調整できる**のが狙い。

調整の観点:
- 街の育つ速度（速すぎる / 遅すぎる）
- 渋滞が起きる閾値（起きなさすぎ / 詰まりすぎ）
- 税収と建設費のバランス（金が余る / 常に足りない）
- マイルストーンの間隔（達成が遠すぎ / 近すぎ）
- 満足度の下がり方（理不尽に感じないか）

**この工程はエージェントだけで完結させない。** 「気持ちよさ」の判定はオーナーが行う。
エージェントの役割は、指示された方向へ数値を動かし、ヘッドレスの長時間実行で破綻がないことを確かめること。

### W2: 性能の最終確認

- **実機（ミッドレンジAndroid想定）でのFPS計測**。ヘッドレスのFPSは13〜21しか出ず使えない
- 予算超過時の段階策（実装書 §17）: ①描画LOD（ズームアウト時に車両を点に）まで。②A*のノード圧縮 ③Worker移行 は**必要になるまでやらない**

### W3: 公開作業

- **Cloudflare Pages** にデプロイ（Gitインテグレーション、main → 本番）
- OGP画像（ゲーム画面のスクリーンショット）・favicon（幾何学図形のロゴ）
- README の公開URL追記、ライセンスの決定
- フィードバック導線（Googleフォーム）
- Lighthouse Performance ≥ 80（モバイル）

**人間（オーナー）の作業**:
- Cloudflare Pages プロジェクト作成とドメイン判断（候補: `machi.example.com`）
- Googleフォームの発行
- ライセンスの決定
- リポジトリを public にするかの判断

### M6 の完了条件

1. 本番URLでスマホ・PC双方から遊べる
2. Lighthouse Performance ≥ 80（モバイル）
3. **オーナーが「公開してよい」と判断する**

## 5. 順序と依存関係

```
M3（街が読める）
  ↓
M4  W1 施設 ─┬→ W2 マイルストーン（施設の解放条件になるので W1 の後）
             └→ W3 エリア拡張（W2 の pop500 で解放されるので W2 の後）
  ↓
M5  W1 セーブ ← データ形式が固まってから
    W2 タイトル/チュートリアル・W3 効果音・W4 設定 は並列可
    W5 モバイル磨き ← 機能が出揃った後
  ↓
M6  W1 バランス（オーナー主役）→ W2 性能 → W3 公開
```

**並列化できるところ**:
- M4 の W1 と、M5 の W1（セーブ）は担当ファイルが重ならないので同時に進められる
- M5 の W2・W3・W4 は互いに独立

**直列にすべきところ**:
- M4 の W1 → W2 → W3（解放条件で繋がっている）
- M6 は全部直列（調整 → 確認 → 公開）

### 委譲の方針

- **根幹の設計判断を含むもの（M4 W1 施設の効果設計、M6 W1 バランス）は Opus に委譲する**
- 仕様が確定していて機械的なもの（M4 W3 エリア拡張UI、M5 W3 効果音）は Sonnet でよい
- 長時間作業は**途中でもコミットさせる**（セッション上限で中断されても成果が残る）

## 6. リスクと注意

| リスク | 兆候 | 対策 |
|---|---|---|
| **施設のバフが効いているか分からない** | プレイヤーが施設を置く動機を感じない | M3 のインスペクタで「この建物は公園のバフを受けている」と見せる。M3 と M4 の設計を繋げること |
| **セーブ形式を後から変えて移行が要る** | M4 で `GameState` の形が変わる | セーブは M4 のデータ形式が固まってから着手する。移行機構は最初から入れる |
| **バランス調整が終わらない** | プレイテストのたびに直しが出る | 「調整のラウンドは3回まで」と決め、それ以上は v1.1 へ送る |
| **公開直前に性能不足が発覚** | 実機FPSが M5 まで一度も測られていない | **M4 完了時点で一度実機計測する**（M6 まで待たない） |

## 8. この計画の弱いところ（正直に）

**M6 のバランス調整の工数がまったく読めない。** 面白さの調整は「あと1回」が繰り返されやすく、
ここで v1 が止まる可能性が最も高い。だから「調整は3回まで、それ以上は v1.1」という撤退線を先に引いてある。

また、**M4 の施設が本当に「置く場所を考える楽しさ」を生むかは作ってみないと分からない。**
バフの半径と効果量が弱すぎれば「置くだけ」になり、強すぎれば「最適解が一つ」になる。
M4 完了時点で一度オーナーに触ってもらい、必要なら M6 を待たずに調整するのが安全。
