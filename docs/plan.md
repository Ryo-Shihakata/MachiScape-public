# MachiScape — 計画書 (v1.0)

> 要件定義書。何を・誰のために・どこまで作るかを定める。
> 実装の詳細仕様は [implementation-spec.md](implementation-spec.md)（SSOT）を参照。

## 1. 概要

**MachiScape** は、Mini Metro / Mini Motorways の系譜に連なるミニマルなまちづくりゲーム。
プレイヤーは道路を引き、区画（住・商・工）を塗り、ユニーク施設を配置して街を育てる。
建物は自動で発展し、住民の車とトラックが道路を実際に走る。渋滞せず人と物が流れる道路網を
考えるパズル的な最適化が核で、ゲームオーバーはなく、じっくり考えられる。

- 形態: 無料公開のWebゲーム（ブラウザのみ、インストール不要）
- 対象: スマホ優先（タッチ操作）、PC対応
- 言語: 日本語先行（i18n対応構造で英語は後追い）

## 3. スコープ

### やる（v1）

- 道路建設（グリッド、橋含む）・撤去・Undo
- 区画3種（住・商・工）の塗り/解除、建物の自動発展・退去
- 個別車両シミュ（自家用車=人の移動、トラック=物流）、渋滞、経路探索
- 経済（税収・建設費・維持費）、RCI需要
- ユニーク施設 5種程度（データ駆動で追加可能に）
- マイルストーン進行、エリア購入によるマップ拡張
- プロシージャルマップ生成（シード指定可）
- モバイル優先UI、ポーズ/倍速、渋滞等のオーバーレイ表示
- ローカルセーブ（自動+手動+エクスポート）、効果音、ライト/ダークテーマ

### やらない（明示的スコープ防衛 — v2以降へ）

- 鉄道・貨物列車・船・バス等の道路以外の交通手段（**ただし設計上のフックはv1で用意する** → 実装書§20）
- クラウド同期・アカウント
- BGM・環境音生成
- 区画の密度レベル（低密度/高密度）
- 英語UI（構造だけ対応）
- 災害・イベント、統計グラフ画面、実績システム
- 対戦・共有などのソーシャル機能

## 4. 技術構成と選定理由

| 層 | 技術 | 理由 |
|----|------|------|
| ビルド | Vite + TypeScript (strict) | 定番。MapCraftと同構成で知見流用 |
| ゲーム描画 | Pixi.js v8 (WebGL) | 車両数千台のスプライト描画をスマホでこなせる。MapCraft実績 |
| UI | React 19 + Zustand | メニュー・HUDはDOMで組む方が速くアクセシブル。Zustandは**UI状態のみ** |
| シミュ | 純TypeScriptモジュール（依存ゼロ） | 固定タイムステップ・決定論。ユニットテスト可能。描画方式を差し替えてもシミュは不変 |
| テスト | Vitest | シミュコアの決定論・経済・経路探索を回帰テスト |
| 保存 | IndexedDB (idb) | 容量・構造化データともlocalStorageより適切 |
| ホスティング | Cloudflare Pages | 静的のみ・無料。v2でWorkers/D1を足せる |

**シミュと描画の分離が最重要の設計判断**: シミュコアは `Math.random` / `Date` / DOM に一切依存せず、
`(state, input) → state` の純関数的な固定タイムステップで動く。これにより
(a) テストで面白さ以外の品質を保証、(b) P0の描画方式比較でコア共用、(c) 将来のWeb Worker移行、
(d) v2クラウド同期（状態が直列化可能）がすべて安くなる。

## 5. ゲームデザイン概要

### 5.1 コアループ

道路を引く → 区画を塗る → 建物が建ち人と物が流れ出す → 税収が入る →
渋滞・未達がボトルネックになる → 道路網を改良し施設を置く → 人口が増えマイルストーン達成 →
新施設・新エリアが解放され、より大きな最適化パズルへ。

### 5.2 空間

- グリッド（1タイル=1建物）。道路はタイルを占有し4方向接続
- 地形: 平地・水（川/湖）・山・森。水は橋（高コスト）でのみ横断可、山は建設不可、森は伐採費で更地化
- マップはチャンク（32×32タイル）単位で拡張。開始1チャンク、人口で購入解放

### 5.3 シミュレーション

- 人: 入居済み住宅から商業・工業・施設へ車が出発。到着成功で満足度↑、渋滞・未達で↓
- 物: 工業が生産、商業が消費。在庫が減るとトラックが配送。品切れは商業の税収・満足度に響く
- 渋滞: 道路タイルごとの車密度で速度低下。ヒートマップで可視化
- 満足度が低い建物は退去（人口減）— これが唯一の「失敗」。ゲームオーバーはない

### 5.4 経済

- 収入: 入居建物からの日次税収。支出: 道路・施設の維持費。建設は都度払い
- 資金が尽きても破産はなく、建設できなくなるだけ（税収でいずれ回復）

### 5.5 ユニーク施設

公園・学校・病院・市役所・スタジアム（初期セット）。データ駆動（マスターテーブル）で追加が容易。
需要発生源（車の行き先になる）+ 周囲バフ（発展促進・満足度）+ マイルストーン解放の3役。

### 5.6 進行

人口マイルストーン（100人、300人、…）で施設解放・報奨金・エリア購入権。エンドレスに続けられる。

## 6. アートディレクション

- Mini Motorways風: フラットな単色図形 + ソフトドロップシャドウのみで立体感
- 画像アセット原則ゼロ。図形はコードで描画（Pixi Graphics → テクスチャ化）
- ライト/ダーク両テーマ。色はデザイントークンで一元管理（区画色: 住=緑系、商=青系、工=黄系 ※トークンで調整）
- アイコンも幾何学図形ベース。日本語UIフォントはシステムフォントスタック

### マイルストーンの再編（2026-07-30・Ryo承認済み）

**M3 の主題を「施設と進行」から「街が読める」に差し替え、以降を1つずつ後ろへずらした。**

理由: プレイテスト①をRyoが実機で実施したところ、**「街が読めないので、楽しいかどうかを
判定できなかった」**という結果になった。M2 の改善要望9点のうち6点も「街で何が起きているか
読み取れない」に集約された。つまり可読性は好みの問題ではなく、**面白さを判定するための前提条件**。
先に施設を足しても判定不能なままなので、順序を入れ替えた。

**バランス調整は M3 に含めず、M6 まで持ち越す**（Ryoの指示）。可読性を上げてから調整しないと、
何が効いたのか切り分けられなくなるため。

詳細な経緯は `docs/decisions.md` の D4、実装計画は `docs/m3-plan.md` §11。

### さらに再分割（2026-07-31・D5）

M3 完了後のオーナーの5要望を受け、**M4 の主題を「施設と進行」から「交通が見える・反応する」へ差し替え**、
施設・進行を M5 へ後ろ倒しした。別系統モデル（GPT-5 high）の設計レビューを踏まえた判断。

**最も重い判断は「動的迂回を弱めにする」こと。** 迂回が賢すぎると、ゲームがプレイヤーの代わりに
渋滞を解いてしまい、「渋滞せず流れる道路網を考えるパズル」という v1 のコアが消えるため。
経緯は `docs/m4-plan.md` §0。

## 8. リスク

| リスク | 影響 | 手当て |
|--------|------|--------|
| 渋滞の手触りが悪い（厳しすぎ/緩すぎ） | 面白さの根幹 | 全定数Tunable化 + 各マイルストーンのプレイテストゲート |
| **動的迂回がプレイヤーの代わりに渋滞を解く** | **v1のコア（道路網パズル）が消える** | 迂回は「弱め」に固定。閾値は難易度そのものとして balance.ts で調整（D5） |
| スマホ性能（車両数千台） | 対象プラットフォームで遊べない | 性能予算を実装書§17で明記。M0から実機計測。Worker移行路を確保 |
| スコープ肥大（交通手段追加の誘惑） | v1が完成しない | §3「やらない」リスト + v2フックは「設計のみ」と明記 |
| P0で方式を決めきれない | 着工遅延 | プロトは操作感の比較のみに限定。判断者はRyo、基準は実装書§19 P0 |
| 需要・経済の数値バランス | 単調 or 詰み | balance.ts一元管理。シミュのヘッドレス長時間実行テストで崩壊検知 |
